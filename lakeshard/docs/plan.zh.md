# 仓库进、缓存出：方案与决策记录（通用版）

日期：2026-11-24。机器只写角色名（`hub` 协调器、`worker-1`…），不写真实主机与内部服务。实验数据与带真实主机名的记录不在本仓库。

## 1 目标

- **输入**：一个 Lean 仓库（Git 链接加提交号，或本地路径）。
- **输出**：这个仓库的构建缓存。别人拿到缓存，放进自己的检出，原版 `lake build` 不用再编译。
- **要优化的**：从输入到输出的墙钟时间（同时记录 CPU·时），以及流程的稳健性。

验收：在小、中、大三档仓库上给出实际的并发效率（第 5 节）。当前可用的是几台共享服务器上合计约 32 核；设计上要为更大的集群留余量。

## 2 流程

```text
取源码 → 环境指纹 → 分析 → 规划 → 并发构建 → 校验 → 打包缓存
                                   ↑ 协调器（自动机）+ 若干 worker + 产物库
```

| 步骤 | 做什么 | 产出 |
|---|---|---|
| 取源码 | 按提交号取一份只读快照；依赖（如 Mathlib）取官方缓存 | 源码快照、依赖产物 |
| 环境指纹 | toolchain、依赖清单、选项、平台的哈希 | 缓存的命名空间；指纹不同的 worker 不混用 |
| 分析 | 只读 import 头建导入图；历史耗时或按行数估计；内存分级 | 图、每个模块的估计耗时 |
| 规划 | 下界 max(最长链, 总工作量 ÷ 总核数)；定 worker 数与线程分配；静态计划只作预估和对照 | 计划文件 |
| 并发构建 | 协调器维护模块状态（等待、就绪、运行、完成、失败、跳过），就绪模块按剩余最长链派给空闲 worker；worker 每个模块直接调 `lean` | 每个模块的产物进产物库 |
| 校验 | 产物哈希；原版 Lake 认可（`lake build --no-build`）；内核重放（抽样或全量，可分发） | 校验报告 |
| 打包缓存 | 内容寻址的对象 + 清单（仓库、提交号、指纹、模块 → 文件） | 缓存目录或压缩包 |

消费侧：`restore` 把缓存放进一份检出，之后原版 Lake 直接可用。

## 3 稳健性靠什么

1. **一切以产物库为准。** 模块“建没建过”只看产物库里有没有对应输入哈希的产物；协调器崩溃或任务被杀，重跑时从产物库恢复状态接着建。续建、增量、去重是同一条路径。
2. **每一步幂等。** 同一个模块建两次结果相同；产物先写临时名再改名，读的人看不到半个文件。
3. **失败隔离与分类。** 一个模块失败，换一个 worker 重试；在两个 worker 上都失败，判为源码问题，只跳过它的下游，其余照常建完并在报告里列出。超时、worker 失联（心跳）按失败处理。
4. **环境不一致当场拒绝。** worker 上报指纹（toolchain、依赖产物哈希、源码路径），与任务不符就不派活。
5. **每个文件校验。** 下载必核 sha256；最后在一份全新组装的目录上让原版 Lake 和内核各过一遍。
6. **全程留痕。** 事件日志（每个模块在哪个 worker、何时开始结束、耗时、内存）、计划文件、报告；逐模块耗时存下来给下一次规划用。
7. **为大集群留余量。** worker 无状态、主动领任务，经网络协议与协调器通信，不依赖共享文件系统；产物库是接口（目录或 HTTP，以后可换对象存储）；调度在 17.5 万个模块、上千个槽位的规模上用“假 worker”做压力测试。

## 4 条件与约束（通用描述）

- worker 机器与他人共用；可用核数少（合计约 32），每台限核、低优先级运行。
- 共享存储（NFS）偶有数秒的卡顿、与他人共用，并非每台机器都能挂载；以后的大集群也未必有共享盘。
- 沙箱平台对每个实例的进程数、存活时间、能否互联有限制；不可信的第三方仓库只在沙箱里建。
- 部分机器的 `vm.max_map_count` 是默认的 65530：Mathlib 规模够用，更大的仓库不够。

## 5 验收：小、中、大三档（只用可信代码）

| 档 | 仓库 | 规模 | 用途 |
|---|---|---|---|
| 小 | 合成仓库 | 几十到几百个模块 | 跑通；每次改动后的回归 |
| 中 | Mathlib 的一个子闭包 | 一两千个模块 | 效率；几分钟一轮，方便调参 |
| 大 | Mathlib 全量 | 约 9 千个文件、247 万行 | 效率；按行数估加速比上限约 25，与约 32 核相配 |

每档报告：单机原版 `lake build`（同样的总核数）、本工具单机、本工具多机的墙钟、CPU·时、峰值内存；实测时长 ÷ 下界及差距来源（等待、传输、启动）；缓存大小、打包与恢复的时间、恢复后原版 Lake 认可；中断后续建、改一个文件后增量重建的耗时与重建的模块数。第三方、AI 生成的仓库只在沙箱里建；更大的仓库（如 GRH、CFSG）留给更大的集群。

## 6 步骤

- **S1 最小闭环**（单机）：协调器 + 直接调 `lean` 的 worker，合成仓库，与 `lake build` 逐字节一致。（已完成，见 `stages.md`）
- **S2 跨机器的形态**（单机模拟）：worker 经 HTTP 向协调器领任务；每个 worker 用自己的本地构建目录；产物库两种实现（共享目录、HTTP）；用互不共享目录的多个进程验证。（已完成，见 `stages.md`；逐次运行记录的格式见 `run-records.md`）
- **S3 仓库进、缓存出**（已完成，见 `stages.md`：`run`/`restore`、输入键与续建、封口、指纹、第 3 节各项的测试、`lakefile.lean`、`--target`；Mathlib 子闭包 96 个模块的 trace 输入哈希与原版一致）：`lakeshard run <仓库>` 一条命令走完第 2 节；`lakeshard restore`；第 3 节第 1–6 项逐项有测试（杀掉重跑、注入失败、指纹不符、损坏的产物）；支持 Mathlib 这样用 `lakefile.lean` 和 module 系统的仓库；解决原版 Lake 对缓存的认可（直接调 `lean` 不产生 Lake 的 trace）。
- **S4 多机实验**：在三台机器上各起 worker（`worker-1`…`worker-3`），做第 5 节的三档验收。
- **S5 规模余量**：假 worker 压力测试（大仓库的导入图、上千槽位）；模拟器按实测校准后外推。

## 7 决策记录

| 日期 | 决定 | 理由 |
|---|---|---|
| 11-24 | 后端：每个模块直接调 `lean`；Lake 分批后端保留作对照 | 原型实测 261 秒，原版 278 秒，Lake 分批 343 秒（2,613 个合成模块）；问题变成纯 DAG 调度 |
| 11-24 | 不把“共享盘上的共享构建目录”作为跨机器的第一形态；改为“各 worker 本地构建目录 + 网络协议 + 产物库接口”，共享盘只是产物库的一种存放方式。共享目录模式保留作对照 | 共享存储有卡顿、与他人共用、并非处处可挂；大集群未必有共享盘 |
| 11-24 | 协调器与 worker 之间用 HTTP（标准库，长轮询领任务），不用共享目录里的任务文件 | 导入链的每一环都在等派发决定；长轮询毫秒级送达、状态集中在一个进程；共享盘上的文件需要跨客户端的原子领取与目录轮询，属性缓存会把数秒延迟加到每一环 |
| 11-24 | 环境从简：多机实验经 SSH 直接在机器上跑，机器之间走内网直连，不依赖共享盘与沙箱；协调器与产物库放在 worker 能连到的机器上，worker 只向外连 | 能跑起来最重要；重点放在调度与切分的正确认知；有的机器不接受入站的高位端口 |
| 11-24 | 产物库默认由协调器经 HTTP 提供（`/v1/store`），也可单独起 `lakeshard store serve` 或用目录 | 一个进程、一个端口；worker 只需连一个地址 |
| 11-24 | 每次运行保存逐次尝试的运行记录（`modules.jsonl`，见 `run-records.md`），时间统一换算到协调器的时钟 | 给调度研究与模拟器校准用 |
| 11-25 | 产物库里的记录按“输入键”存放（sha256：环境指纹、模块名、源文件哈希、库选项与参数、各导入模块的键）；构建前先查键，只建缺的 | 续建、增量、去重是同一条路径（第 3 节第 1 条）；键随源码或任一上游变化而变 |
| 11-25 | 环境指纹包括 toolchain 与 `lean --githash`、平台、源码绝对路径、Lake 配置、manifest、各依赖构建的摘要（依赖每个模块 `.trace` 里的 depHash 与产物哈希）；worker 先取配置、自算指纹再注册，不符即拒 | 依赖构建的摘要读小文件即可，不必哈希几 GB 的 `.olean`；拒绝发生在派活之前 |
| 11-25 | 让原版 Lake 认可直接后端的产物：“封口”时跑原版 `lake build`，用 `LAKE_OVERRIDE_LEAN` 与 `LEAN_SYSROOT` 指向一个符号链接拼成的 toolchain 目录，其中 `bin/lean` 是从产物库拷产物的垫片；trace 由 Lake 自己算、自己写 | 不重写 Lake 的哈希（随版本变）；实测 trace 的输入哈希与普通 `lake build` 一致（4.33.1、4.35.0，含 module 文件）；`lake build --old` 只认修改时间、不写 trace，不可用 |
| 11-25 | 失败分类：同一模块在两个不同 worker 上编译出错即判为源码问题，不再重试；worker 失联、超时、导入产物损坏不计入 | 换机器仍失败就不是环境问题；损坏的产物由协调器删掉记录与坏对象、重建该模块 |
| 11-25 | `lakefile.lean` 用 `lake translate-config toml` 译成 TOML 放进 `.lake/lakeshard/`，只在被检查过的范围内信任：`check-setup` 对照真实 Lake 构建，`restore` 后用原 `lakefile.lean` 跑 `--no-build` | Lake 自称翻译有损；实测 Mathlib 子闭包 96 个模块 setup 与 trace 输入哈希全同 |
| 11-24 | 验收三档只用可信代码（合成、Mathlib 子闭包、Mathlib 全量） | 不依赖沙箱就能拿到效率数字；第三方仓库留给沙箱 |
| 11-24 | 沙箱的构建档位就绪之前，多机实验经 SSH 直接在机器上跑：只跑可信代码；每台限核、低优先级；只用专用目录；不用管理员权限、不改系统配置；跑完清理 | 最快拿到多机的工程验证与效率数字；对其他用户的影响不超过沙箱本来被允许的量 |
| 11-24 | 目标函数：以墙钟时间为主，同时记录 CPU·时 | 关心“更快”；成本留作对照 |
| 11-24 | 本仓库保持通用：机器只用角色名，真实主机、地址、内部服务名、其他私有项目名不进仓库 | 这是“大型仓库多机构建”的通用项目 |

## 8 风险

- 直接调 `lean` 时参数还原不完整，产物与 Lake 不一致：每个新仓库先用 `lakeshard check-setup` 与 Lake 对比。
- Lake 不认直接调 `lean` 的产物：若补不出 trace，最后一遍改用 Lake 分批后端“封口”。
- 共享机器上别人的负载让计时抖动：每个数字跑三次取中位数，同时记录当时的机器负载。
- 可用核数少（约 32）：加速比的结论只能说到这个范围，更大范围靠模拟器外推和之后更大集群上的实测。
