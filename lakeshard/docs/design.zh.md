# 大型 Lean 仓库的多机构建与复用：原理、探索记录与“infra + 模型”方案

> 正文中的 `research/…` 对应本仓库 `docs/research/`。原型脚本（`dbuild.py`、`dag_stats.py` 等）、调研报告和实验数据未放入本仓库。

日期：2026-11-23。代码即本仓库；调研报告与实验数据未放入本仓库。

标记沿用：**【事实】** 查到或实测的（带出处或数据文件），**【估算】** 由事实推出的数，**【设想】** 还没验证的判断。

## 0 一页摘要

- **要解决的问题**：大仓库（RH 归档 17.5 万个模块、CFSG 4,310 万行）在一台机器上要建 6–22 小时；做实验时反复重建，等不起。目标有两个：**第一次构建尽量快**（多机并发），**之后尽量不重建**（复用产物）。
- **别人怎么做**（第 2 节，读了一手材料）：主流是“一台大机器建，其他人下载缓存”（Mathlib、CFSG、RH 社区 CI 的增量缓存）。多机构建有两例：Sutherland 的 8×192 核（逐文件直接调 `lean`，一小时出头），Omega Institute 的 GitHub runner 分片（按“到 `Main` 的剩余权重”凑包、内容哈希作片键、每片一次 `lake build`、产物存 GitHub Release）。仓库之外，Isabelle 早有成熟的集群构建（启发式排程几秒求解、关键任务给快机器和多线程、构建中定期重排）。我们从中借了 10 条机制（2.2 节）。
- **原理**（第 3 节）：Lean 的构建单位是模块，模块之间只通过 `.olean` 文件交接；Lake 判断“要不要重建”只看内容哈希（源文件、导入模块的哈希、选项、toolchain），不看路径和机器。所以只要各机器的源码路径、toolchain、依赖都相同，任何一台建出的产物都能拿到另一台继续用。能并发到多少，由导入图的关键路径决定。正确性最后靠内核复核，不靠构建机。
- **探索过程**（第 4 节）：做了 10 组实验。直接调 `lean` 的原型、Lake 原生的分批构建都能做到与 `lake build` 逐字节一致；**静态分片被实测否定**（等整片完成，关键路径被拉长 3.5 倍），改用运行时动态批次；单机模拟的开销约 20%；一个依赖 Mathlib 的中型私有工程被一个 5 分钟的文件卡住，多机无用。过程中发现并修掉 4 个程序错误。
- **方案**（第 5 节）：分五层。**分析层**（工具：导入图、历史耗时、CI 日志、内存分级）→ **规划层**（模型读分析结果，定策略与参数，产出可校验的计划文件）→ **执行层**（infra：确定性的调度器、执行器、worker、内容寻址产物库，每秒几十次决策，不经过模型）→ **监控层**（infra 产生事件，模型诊断异常、通过受限的动作接口干预）→ **校验与发布层**（组装、复核、发布可复用的缓存）。每次运行与每个决策都留结构化记录。
- **需要讨论的**（第 7 节）：远程执行器用什么（SSH、队列还是 HTTP）、产物库放哪里、模型干预的权限边界、超大仓库用 Lake 后端还是直接调 `lean` 的后端、谁来提供 CI 日志与历史耗时。

## 1 目标与约束

1. **快**：第一次构建的时间逼近关键路径，而不是“总工作量 / 单机核数”。
2. **可复用**：同一仓库的新提交只重建变了的模块；别人可以直接取用我们的产物（与 Lake 的缓存格式兼容）。
3. **可信**：构建机执行仓库里的元程序，视为不可信；结论只来自可信机器上的内核复核。
4. **可记录、可复现**：大规模并发时出了问题要能回放；每次实验的参数、过程、结果都留档。
5. **约束**：源码当不可信数据，大仓库只在沙箱里建；不从头造轮子，能用 Lake 原生机制就用。

### 2.1 已有做法

| 做法 | 谁 | 机制要点 | 效果与局限 |
|---|---|---|---|
| **单机构建 + 分发缓存** | Mathlib | CI 单机构建；每个模块的缓存键混合了 toolchain/lakefile/manifest、源文件内容与所有 import 的哈希，产物 `<哈希>.ltar` 放在 `cache.mathlib.org`；下游 `lake exe cache get` | 用户免建；第一次构建不变快 |
| 同上 | CFSG（Axiom） | 单机（96 vCPU / 3 TB，22.5 小时；重构后 6 小时），产物发布到自己的 Lake 缓存 | 同上 |
| 单机 + 增量 + 分发缓存 | RH 社区 CI | 每个 PR 一台自托管大机器：按清单（模块、输入哈希、`.ltar`、sha256）恢复基线产物，在无网络 bubblewrap 沙箱里跑原版 `lake build -o`，只重建输入哈希变了的模块；新产物作为增量发布，按输入指纹复用；默认 `min(8, 核数)` 并发，内存上限取物理内存 80%，任务时限 24 小时；重、轻两个 runner 池 | 每个 PR 只付改动的代价；仍是单机 |
| **多机，按闭包切片，CI runner 执行** | Omega Institute | 导入图用 `git grep` 抓 import 行；切片分两轮：地基片（每片 ≤400 个模块、≤2.5 MB 源码），再按波次凑包（就绪模块按“到 `Main` 的剩余权重”取，只差本包的后继并入，每包 20–180 个模块）；片键 = SHA-256（toolchain/manifest/lakefile、各模块源码 blob、上游片键）；每片在托管 runner 上：下载上游片的 `tar.zst`（存于 16 个按键首字符分桶的 GitHub prerelease，校验摘要）→ `lake --no-build` 确认 → `lake build +M:olean …` → 打包上传 → 删除输出、从包恢复、再 `--no-build` 自检；调度器每 60 秒轮询，就绪片按剩余权重排序，每批派 28 个，去重（同键已存在、在跑或 180 秒内刚派），每片最多 3 次，4 小时后交给新一轮接着跑；最后在自托管机上建 `Main` 并检查五个定理与公理白名单 | 8,490 片、36 层（README）；不需要自己的机器；受 runner 时限、内存与 GitHub API 节奏限制；文件里没有总耗时 |
| **多机，按模块直接调 `lean`** | Sutherland（MIT） | 8 台 192 核机器，逐文件直接调 `lean`，传入 Lake 会给的模块名、包名与 lakefile 选项；所有机器同一路径 `/home/ubuntu/grh/src/lean`；Fable 5.2 编排（Zulip）；之后把导出分发到多台机器各跑一个内核 | 一小时出头（Zulip 11-20 16:55 UTC）；不在沙箱里；脚本未公开 |
| 单机，自写调度器 | 第三方（二手文章） | 288 核机器上 Lake 因锁争用降到每分钟 30–50 个模块；改用自写的关键路径优先调度器后 2 小时跑完；漏传 `-R` 曾导致 425 个模块失败 | 仅二手来源，未核实 |
| **集群构建** | Isabelle AFP（Huch & Wenzel, ITP 2024） | 主节点经 SSH 管 worker，各节点用本地 SSD，不用共享盘；共享状态与产物（压缩后的 heap，切成约 50 MiB 的块）放 PostgreSQL；耗时预测用历史日志 + 基准 session 换算机器 + Amdahl 插值线程数，并故意略微高估；排程建模为多模式资源受限项目调度，用启发式在几秒内求解：找出关键 session 给最快的机器，非关键 session 按耗时分档给 1/4/8 线程，构建中每 5 分钟重排一次 | AFP 35 分 40 秒（单节点 4–8 小时），CPU 时间是墙钟的 100 倍以上；异构集群上比贪心调度快一倍多；冷启动要 7–8 次构建积累历史才收敛 |

其他已核实的数据：MIT 沙箱重建（一台 192 核 EPYC 9R45）`LEAN_NUM_THREADS` 从不设经 96、64、40 最后定在 64 并绑核，约 8 小时，脚本注释说 192 线程时 Lake“大部分时间在争一把内部锁”（`sandbox-build-continue.sh`）；导出约 1 小时 25 分；nanoda 80 线程 27 分 42 秒、峰值约 89 GB。内核复核方面：官方内核的并行重放还在 RFC #15569（单线程预计 1–2 周的导出，342 线程 83 小时跑完），comparator PR #99 加了可选的并行重放。

### 2.2 从别人那里借什么

| 借来的机制 | 出处 | 我们怎么用 |
|---|---|---|
| 内容哈希作缓存键，上游键折进下游键 | Mathlib、Omega、Lake | 产物库按 Lake 的输入哈希索引；不自造键 |
| 原版 Lake 做每批的增量判断与自检 | Omega、RH 社区 CI | worker 用 `lake build +M…`；建完删输出、从产物库恢复、`--no-build` 自检（待加） |
| 剩余关键路径优先 | Omega、Isabelle、第三方调度器 | 已实现（动态批次的挑选规则） |
| 只差本批的后继并入同批 | Omega 第二轮切片 | 已实现，但在运行时做、用实测耗时当权重 |
| 关键任务给最快的机器和更多线程，非关键按耗时分档给线程 | Isabelle | 待做（E9 的损失正是关键批次线程太少） |
| 历史耗时 + 换算 + 略微高估，构建中定期重排 | Isabelle | 有历史耗时；换算、高估、重排待做 |
| 节点本地盘 + 中心化的状态与产物存储，不用共享盘 | Isabelle | 产物库接口已留；远程实现待做 |
| 增量：只重建输入哈希变了的模块，增量单独发布 | RH 社区 CI | 产物库天然支持；“新提交只建增量”的流程待做 |
| 可信与不可信产物分区 | Mathlib（master 与 fork 分容器）、RH 社区 CI | 构建产物先进“未复核区”，复核后提升 |
| 绕开 Lake 的单机调度锁 | MIT、第三方调度器 | 每个 worker 的线程数不宜过高；多 worker 分摊 |

**结论**：“单机 + 缓存”解决复用，不解决第一次构建；多机的先例都绕开了 Lake 的单机调度，要么每片一次 `lake build`（Omega），要么直接调 `lean`（MIT）。我们的方案与 Omega 最接近，区别是**运行时动态凑批、用实测耗时排优先级、在自己的沙箱上跑而不受 CI 平台的节奏限制**，并补上 Isabelle 的排程经验与可信复核。

## 3 原理机制

### 3.1 构建的依赖结构

- 一个模块（一个 `.lean` 文件）编译成 `.olean`（给导入者用的二进制环境）、`.ilean`（给编辑器的位置信息）、`.c`（编译后端）。导入者只读取被导入模块的 `.olean`，**模块之间没有别的交接**。【事实】
- 所以构建是一张有向无环图上的任务调度：节点是模块，边是 import。两个数决定一切：**总工作量 W**（所有模块的耗时之和）和**关键路径 CP**（最重的一条导入链的耗时之和）。任何调度的时长 ≥ max(CP, W / 核数)，加速比上限是 W / CP。【事实，调度理论】
- RH 归档：W 约 300–600 核·时，CP 约 1–1.5 小时，W/CP 约 400（导入图分析与模拟，数据未放入本仓库）。一个依赖 Mathlib 的中型私有工程（230 个模块）：W 2,066 秒，CP 444 秒，W/CP 4.65。【估算 / 实测】

### 3.2 Lake 怎么判断“要不要重建”，以及为什么产物能跨机器搬运

- Lake 为每个模块写一个 `.trace`：记录输入哈希（源文件内容哈希、各导入模块的哈希、`leanOptions`、`moreLeanArgs`、模块名、包名、toolchain 版本），以及输出文件；另有 `.olean.hash` 等哈希文件。构建前 Lake 重算输入哈希，与 trace 一致且输出在，就跳过。【事实，本机读 trace 与 Lake 4.33.1 源码】
- trace 里的输入哈希**只含内容哈希**；源文件路径只出现在说明文字里，不参与哈希。所以把一台机器建出的 `.olean/.ilean/.c/.trace/.hash` 拷到另一台机器的构建目录，Lake 认为它们是最新的。【事实，本机实测：拷入 315 个模块的产物后，Lake 只重建缺的那 1 个；`lake build --no-build --rehash` 通过】
- 这正是 Mathlib 缓存、RH 社区缓存能工作的原因，也是我们多机构建的基础：**一个 worker 只要拿到它这批模块所导入的全部产物（连同 trace），就能用原版 `lake build` 只建这一批**。【事实】
- Lake 的哈希是 64 位的非密码学哈希（Lake 帮助文本自己说明），所以我们的产物库另用 sha256 做寻址与完整性校验。【事实】

### 3.3 产物逐字节相同的条件

- 同一 toolchain、同一依赖构建（如 Mathlib 官方缓存）、同一选项；**源文件的绝对路径相同**：Lean 4.33 把带 linter 消息的模块的源文件绝对路径写进 `.olean`（`lintLogExt`）。RH 归档里 98,219 / 175,187 个 `.olean` 因此依赖路径。【事实，社区 `NOTES.md`；本机原型复现：换路径后恰好那 32 个带警告的模块不同】
- 已知的不确定性：Lean 4.33.1 的并行 elaboration 有竞争，RH 里 1 个模块（`LocModel`）每次结果可能不同，4.36 修复；导出不受影响。【事实，Zulip 11-22 04:01 UTC】
- 本机模拟多机时，所有 worker 共用同一个源码目录，只换构建目录（Lake 允许外置 lakefile `lake -d 工程 -f 配置`，`buildDir` 可设为绝对路径，产物不变）。【事实，本机实测】

### 3.4 正确性分三层，最后一层才是结论

1. **产物一致**：与参照构建逐字节比对，或与公开的 `.olean` 清单比对（如 Sutherland 的 `project-oleans.sha256`，需同一路径构建）。
2. **Lake 一致**：组装后的构建目录上 `lake build --no-build --rehash` 通过，说明每个模块的输入与输出都对得上。
3. **逻辑正确**：在可信机器上让内核重放——逐模块 `leanchecker`（可分发），或导出后用多个独立内核与 `lake comparator` 判定。构建机交出的错误产物只会让这一层失败，不会让假定理通过。

前两层排查“构建过程有没有出错”，第三层才回答“证明对不对”。

### 3.5 资源模型

- `import` 用 mmap 把整个导入闭包的 `.olean` 映射进来；同一台机器上的进程共享这些页缓存，私有内存相对小（本机 `import Mathlib`：私有 0.54 GB，映射 7.5 GB，52,301 个映射区）。【事实，本机】
- 因此内存需求按“闭包大小”分级：RH 里闭包中位数 720 个模块，只有 27 个模块的闭包超过 5 万（导入近 94 GB 的 `.olean`），这几十个要放到大内存机上；顶端模块的映射区数超过 Linux 默认的 65,530，要调高 `vm.max_map_count`。【估算】
- 每次 Lake 调用都要先核对整个导入闭包的 trace：本机合成工程 0.4–1.8 秒，依赖 Mathlib 的工程 4–6 秒，RH 全量 `--no-build --rehash` 44 秒（社区 `CACHE.md`）。批次不能太碎。【事实】

### 3.6 调度原理

- **列表调度，剩余最长路径优先**：每次从“导入都已建好”的模块里挑剩余最长路径最大的（关键路径上的先建）。这是 Isabelle 与经典 DAG 调度的通用做法。
- **就近**：优先把模块派给已经持有它大部分导入产物的机器，少传数据。模拟显示，就近调度下 30 秒以内的跨机延迟基本不影响总时长；若每条依赖都要等 30 秒，总时长翻倍以上（RH 的导入链有 203 层）。【估算，调度模拟】
- **批次**：一次 Lake 调用建一批模块，摊薄 Lake 的固定开销；但一批要整体完成后下游才能开始，批太大会拉长关键路径。动态凑批（运行时按优先级取就绪模块、沿导入链扩展到成本预算）比预先切好的静态分片好（第 4 节 E5、E6）。

| E4 | 原型：直接调 `lean` + 内容寻址库 | `scripts/dbuild.py`：一个进程模拟 4 台机器 × 3 槽；照 Lake 的方式写 `--setup` 文件调 `lean`；产物只能经 sha256 寻址的库流动 | 316 个模块：15.3 秒（`lake build` 15.9 秒），316/316 逐字节一致，leanchecker 全过，注入的失败自动重试；2,613 个模块也全部一致 | 可行，开销最低；但不产生 Lake trace，下游不能直接用原版 Lake 复用。保留为超大仓库的备选后端 |
| E5 | 路径依赖验证 | 同上，每台“机器”用不同的源码路径 | 恰好 32 个带警告的模块产物不同，`.ilean` 全同 | 采用：所有机器必须用同一绝对路径 |
| E6 | Lake 行为探测 | 外置 lakefile、绝对路径 `buildDir`、把别处的产物连同 trace 拷进新构建目录 | 都可行；Lake 只重建缺的模块；`--no-build --rehash` 通过 | 采用：worker 用原版 Lake，产物天然带 trace，可直接做成缓存 |
| E7 | 静态分片 | `lakeshard` 的静态计划（按拓扑序并入导入所在分片，位集保证分片图无环），316 个模块要 24 片 | 实际切出 72 片；墙钟 31.3 秒（`lake build` 15.9 秒）；分片级关键路径是模块级的 3.5 倍 | **否定**为默认方案：一片必须整片完成，下游才能开始。保留用于导出给“只能按片跑”的环境（如 GitHub runner） |
| E8 | 动态批次 | 运行时凑批：就绪模块按剩余最长路径挑，沿导入链扩展到成本预算 | 316 个模块：20.5–21.1 秒（预算 20/60）；12 个 worker × 1 线程 24.7 秒；2,613 个模块：342.7 秒（`lake build` 277.6 秒），7,839 个文件逐字节一致，`--no-build --rehash` 与 leanchecker 2,613/2,613 通过 | 采用为默认。单机上开销约 23%，主要是每批一次 Lake 启动（合成工程 0.4–1.8 秒） |
| E9 | 真实工程（依赖 Mathlib） | 一个依赖 Mathlib 的中型私有工程，230 个模块：参照 `lake build` 8 线程，对比 4 个 worker × 2 线程 | 参照 503.2 秒；我们 596.7 秒，27 批，0 失败；690 个文件逐字节一致，`--no-build --rehash` 与 leanchecker 229/229 通过；关键路径 444 秒，其中一个文件占 317 秒 | 正确性过关；**这个工程多机无用**（加速比上限 4.65）。多出的 94 秒：关键链上的批次掺了别的模块又只有 2 线程，且下游要等整批完成。→ 改进方向：批内逐模块回报、关键批次多给线程 |
| E10 | 内核复核的成本 | 组装后逐模块 `leanchecker` | 2,613 个合成模块 1,085 秒（8 并发）；上述 Mathlib 工程 1,368 秒（4 并发）；库根模块会触发整棵子树重查，在 macOS 上卡住 33 分钟后被停 | 复核比构建还慢，必须和构建一样分发；要绕开 `leanchecker` 的前缀语义 |

过程中发现并修掉的程序错误（都有测试覆盖）：

1. 静态分片：模块并入分片后，依赖该分片的其他分片的祖先集合没有同步更新，可能放过环 → 同时维护祖先与后代位集；加随机图测试。
2. 动态调度：一批成功后，同批的后继模块被重复放回就绪集 → 先整批记完成再放行下游，增加“运行中”集合，派发时断言所需模块都已完成。
3. `build` 把合并后的耗时写回了输入的历史文件，覆盖了参照构建的逐模块耗时（参照合计与最慢模块的数字另有保存）→ 只写工作目录里的 `history.json`；参照构建另存完整日志。
4. `leanchecker X` 会检查所有以 `X.` 开头的模块 → 这类模块单列，可跑可跳过，报告里写明。

## 5 方案：infra 与模型的分工

### 5.1 分层

```text
 ┌──────────────── 模型（规划与判断，低频）────────────────┐
 │ 读分析报告 → 选策略、定参数 → 写计划文件（可校验）          │
 │ 读事件摘要 → 诊断异常 → 调用受限的动作接口                  │
 │ 读结果 → 写报告（分清事实、估算、设想）                     │
 └──────▲──────────────────────────────┬────────────────────┘
        │ 分析报告 / 事件摘要 / 结果     │ 计划文件 / 动作（都记日志）
 ┌──────┴──────────────────────────────▼────────────────────┐
 │ infra（确定性，高频）                                       │
 │ 分析层：导入图、历史耗时、CI 日志、内存分级、风险扫描        │
 │ 执行层：协调器（每秒几十次派发）、执行器、worker、产物库      │
 │ 校验层：组装、--no-build --rehash、逐字节比对、内核复核       │
 │ 发布层：Lake 兼容缓存（输入哈希 → 产物），增量复用            │
 └──────────────────────────────────────────────────────────┘
```

原则：**模型不进每个模块的调度回路**（17.5 万次决策，要毫秒级、可复现），只在“开始前”“出异常时”“结束后”介入；它的每个决定都落成计划文件或一条动作记录，infra 负责校验与执行。

### 5.2 分析层（infra 工具，产出给模型与调度器）

| 工具 | 输出 | 现状 |
|---|---|---|
| 导入图 | 模块、边、深度、各层宽度、闭包大小、外部依赖 | `lakeshard analyze`（只读 import 头）；Omega 用 `git grep` 做同样的事；可用 `lake query --json +M:imports` / `+M:transImports` 互证（本机实测可用）；import-graph 包（`lake exe graph`，需先构建）可出 `.dot`/`.html` 图 |
| 历史耗时 | 每个模块的实测秒数 | 从 Lake 输出的 “Built X (时间)” 解析（本机 4.33.1/4.35.0 非交互输出每个模块一行）；来源：我们自己的运行、参照构建、**用户提供的 CI 日志**（GitHub Actions 日志可经 REST 接口批量下载）；Mathlib 的 radar 只有逐模块指令数 |
| 关键路径与机器数估算 | 给定 N 个槽位的预计时长、加速比上限、最慢的若干模块 | `lakeshard analyze --history --slots …` |
| 内存分级 | 每个模块闭包内 `.olean` 的总字节，划分普通/大内存 | 有闭包大小；按字节分级待做 |
| 风险扫描 | `import Lean`、`run_cmd`、`addDecl`、`native_decide` 等出现位置 | RH 审查里做过（正则，静态），待并入工具 |
| 环境检查 | toolchain、依赖是否已有缓存、`max_map_count` | 待做（worker 端 `doctor`，参考社区 `ci-runner.py doctor`） |

### 5.3 规划层（模型做什么）

模型读分析报告，回答这些问题并写进计划文件（JSON，infra 校验后执行）：

- **值不值得多机**：W/CP 小（如上述 Mathlib 工程的 4.65）就直接单机 `lake build`，或者先处理关键路径上的重文件；W/CP 大（RH 约 400）才分发。
- **机器规模与分级**：按模拟确定槽位数（加速比曲线变平处），按内存分级确定大内存机数量。
- **后端与批次**：Lake 后端（产物带 trace，可直接做缓存）还是直接调 `lean` 的后端（开销最低）；批次预算按“Lake 每次调用的固定开销 × 20”起步。
- **特殊模块**：关键路径上的重文件单独成批、多给线程；已知不确定的模块；需要大内存的顶端模块固定到大机器。
- **分阶段放大**：先跑一小块（例如闭包最小的一层）验证环境与逐字节一致，再放开全量。
- **校验强度**：比对哪份参照（参照构建、公开清单），内核复核用哪几种、分发到几台。

### 5.4 执行层（已实现的部分在 `lakeshard`）

- **协调器**：维护模块状态（等待 / 就绪 / 运行 / 完成 / 失败 / 跳过），动态凑批，就近派发，重试（换机器，失败批拆成单模块），失败只影响下游。
- **排程改进（借自 Isabelle，待做）**：按历史耗时找出关键模块（所在路径超过关键路径长度的某个比例），给它们最快的机器、独占的批次和更多线程；非关键批次按耗时分档给线程；构建中定期（如每 5 分钟）按实际进度重排。
- **执行器接口**：`submit(worker, job)` / `poll()`。现有本机多进程执行器；远程执行器（SSH、队列或 HTTP）按同一接口加。
- **消息**：`ShardJob`（要建的模块、需要的模块、工程与 toolchain、产物库位置）、`ShardResult`（产出的记录、耗时、CPU、峰值内存、传输字节、错误、日志尾）、`ModuleRecord`（每个产物文件的路径、sha256、大小），全部是 JSON。
- **worker**：持久工作区；取回所需产物并校验 → 原版 `lake build +M…` → 上传新产物；Lake 若重建了批次以外的模块就判失败（说明环境不一致）。
- **产物库**：sha256 寻址的对象 + 每模块一条记录；现在是目录，接口留给 HTTP / S3。

### 5.5 监控与干预（模型 + infra）

- infra 把事件写成 `events.jsonl`（每批一行），并定期汇总：吞吐、各机利用率、失败、最慢的运行中批次、与预计时长的偏差。
- 模型在这些时刻被唤醒：失败重试用尽、某批超过预计时长的若干倍、某机器反复失败、整体落后计划。
- 模型能做的动作是一组受限接口，每次调用都记录原因：重排某模块的优先级、改批次预算、把模块固定到某类机器、提高超时、加减机器、暂停与恢复。它不能改源码、不能改校验标准。
- 典型诊断：“Lake 重建了批次以外的模块”→ 多半是 toolchain 或依赖不一致；“内存溢出”→ 该模块升到大内存等级；“同一模块在不同机器上都失败”→ 源码问题，不是环境问题。

### 5.6 校验与复用

- 组装 → `lake build --no-build --rehash` → 与参照逐字节比对 → 内核复核（逐模块 `leanchecker` 分发到各机器；需要时导出后跑独立内核与 comparator）。
- **复用**：产物库按 Lake 的输入哈希索引，新提交只建输入哈希变了的模块（社区 CI 的做法）；需要给别人用时，导出为 Lake 原生缓存格式（`lake build -o` 的映射 + `.ltar`），对方 `lake cache get` 即可。

### 5.7 记录

每次运行固定留下：计划文件、`events.jsonl`、`report.json`（总耗时、CPU、内存、传输量、失败）、`history.json`（逐模块耗时，供下次规划）、校验结果，以及模型的决策日志（时间、观察、动作、理由）。实验台账按第 4 节的格式累积（目的 / 做法 / 结果 / 结论 / 是否采用）。

## 6 放大到 RH 级别时的问题与对策

| 问题 | 对策 | 状态 |
|---|---|---|
| 每次 Lake 调用要核对整个闭包的 trace（RH 全量 44 秒） | 顶端批次要粗；或改用直接调 `lean` 的后端，最后统一生成 trace | 设想；直接调 `lean` 的原型已有 |
| 一批要整批完成，下游才能开始 | 批内逐模块回报：解析 Lake 输出，一个模块建好就上传并放行下游 | 设想 |
| 关键路径尾部：最后约 10 个模块各要导入几乎全部 `.olean`，串行 | 放在同一台大内存机上，页缓存保持热 | 设想 |
| 每台机器最终要持有 90% 以上的产物（约 100 GB） | 每台按全量配盘；用压缩包传（社区数字：17.5 万个 `.ltar` 共 4.9 GB） | 估算 |
| 内存：顶端模块约 100 GB | 内存分级调度 | 估算 |
| 内核复核比构建还慢 | 逐模块 `leanchecker` 与构建一样分发；完整导出用多线程独立内核 | 设想（本机已测单机成本） |
| 不可信代码 | worker 在沙箱里跑，不放凭据；复核在可信机器上做 | 设计如此 |

## 7 需要讨论的问题

1. **远程执行器**：用 SSH 直连沙箱、消息队列，还是一个 HTTP 协调服务？取决于沙箱平台能提供什么（沙箱平台的接口、网络互通、单机规格上限）。
2. **产物库放在哪**：对象存储（S3 兼容）、协调机本地盘加 HTTP，还是共享文件系统？要多大带宽？
3. **模型干预的边界**：哪些动作模型可以自动执行，哪些要人确认（例如加机器涉及费用）。
4. **后端选择**：Lake 后端（产物带 trace，复用方便）与直接调 `lean` 的后端（开销最低、要自己生成 trace）是否两条都维护。
5. **数据来源**：CI 日志与历史耗时由谁提供、什么格式（GitHub Actions 日志、Lake 输出、我们自己的 `history.json`）。
6. **验收标准**：大仓库跑完后，以哪几层校验为准（逐字节比对哪份清单、内核复核覆盖到什么程度）。
