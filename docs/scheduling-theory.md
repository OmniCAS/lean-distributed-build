# 调度理论：这个问题的标准形式、已知的最优结果，以及对我们的结论

日期：2026-11-24。作者：总控会话；2026-11-25 研究会话按原文核对了第 2–4 节的文献并改正（改动列在文末），第 5 节按新数据改正。论文以“作者 年份”引用，对应 `REFERENCES.md` 的 T 类；系统的出处用 [S…] 编号，公开数据用 [D…] 编号。模拟数字来自 `study/results/`；Mathlib v4.34.0 的实测 trace 与黎曼猜想归档的模型见 `docs/study-report.md`。

## 1 标准形式

用调度理论的记号，我们的问题是

> **P | prec | C_max**：m 台相同的处理机，任务之间有先后约束（一张有向无环图），目标是最小化完工时间。

节点是模块，边是 import，任务时长 p_v 是编译耗时，处理机数 C 是总核数。三个扩展各对应一类已有的模型：

| 现实因素 | 模型 | 说明 |
|---|---|---|
| 机器快慢不同 | Q 或 R \| prec \| C_max | 异构处理机 |
| 产物要在机器间传 | P \| prec, c_ij \| C_max | 带通信延迟：u、v 不在同一台机器时，v 要晚 c_uv 才能开始 |
| 一个文件可以用多个线程 | P \| prec, any \| C_max | 可塑任务（moldable/malleable）：任务占 k 个核时耗时 p_v(k) |
| 耗时事先不知道 | 在线、non-clairvoyant | 调度时只知道图，不知道 p_v |

## 2 两个界和一个“拐点”

记 W = Σp_v（总工作量），CP = 最重的一条链（关键路径）。

- **下界**：任何调度都有 T ≥ max(W/C, CP)。
- **Graham 界（1966/1969）**：任何“只要有就绪任务和空闲核就开工”的调度（列表调度，不管按什么顺序挑）都满足
  T ≤ W/C + (1 − 1/C)·CP。
  证明思路：看最后完成的那条链；链上没有任务在跑的每个时刻，所有核都必须是忙的（否则那条链上的下一个任务早就该开工了），所以空闲核·时至多 (C−1)·CP。
- 令 **x = C·CP / W**（核数相对“仓库可并行度 W/CP”的比例）。由上面两式：
  T / 下界 ≤ 1 + (1 − 1/C)·min(x, 1/x)。

这一条不等式就是全局图景：

| 情形 | x | 任何贪心调度离下界 | 含义 |
|---|---|---|---|
| 核数远少于可并行度 | x ≪ 1 | 至多 1 + x | 时长 ≈ W/C，线性加速，**调度顺序几乎无所谓** |
| 拐点 | x ≈ 1 | 至多 2 − 1/C | **只有这里调度算法有发挥空间**，最多差一倍 |
| 核数远多于可并行度 | x ≫ 1 | 至多 1 + 1/x | 时长 ≈ CP，加机器没用，**只有缩短 CP 才有用** |

代入：Mathlib（实测 W/CP = 36.6）在 16 核上 x ≈ 0.44，三机 32 核 x ≈ 0.87，48 核 x ≈ 1.3；黎曼猜想归档（按 Mathlib 校准的模型 W/CP ≈ 510–536）在 48 核上 x ≈ 0.09，在 512 核上 x ≈ 1。

下界 max(W/C, CP) 本身不紧（它不反映“图在某些阶段很窄”）。更紧的经典下界是 Fernandez–Bussell（1973，IEEE Trans. Computers 22(8)）：让每个任务待在长度为 CP 的调度允许的“最早—最晚开始”窗口里，算出任一时间窗 θ 内必须完成的最少工作量 R(θ)；则 T ≥ CP + max_θ (R(θ)/C − |θ|)（θ 取整个 [0, CP] 时就是 W/C）。要说“离最优还有多远”，应当用这个界。【实测】在 89 个证明了最优的子图上，它的中位数恰好等于最优，最坏低 8%；简单下界最多低 17.5%（`docs/study-report.md` 3.8 节）。

## 3 理论上的最优算法：有什么，没有什么

| 问题 | 结论 | 出处 |
|---|---|---|
| 一般情形求最优 | NP 难（处理机数是输入的一部分时，单位时长的任务也难）；固定台数 m ≥ 3、单位时长是否 NP 难至今未解决 | Ullman 1975（JCSS 10(3)） |
| 近似比的下限 | 好于 4/3 是 NP 难的；在 Bansal–Khot 的唯一博弈猜想变体下，好于 2 − ζ 也不可能（单位时长即成立，处理机数是输入的一部分） | Lenstra–Rinnooy Kan 1978（Oper. Res. 26(1)）；Svensson 2010（STOC；SICOMP 40(5) 2011） |
| 贪心的保证 | 任何列表调度 ≤ (2 − 1/C)·最优 | Graham 1966（BSTJ 45） |
| 结论 | **在上述猜想成立的前提下，最坏情况里贪心已经是能做到的最好**；不存在“理论最优且可算”的通用算法 | 上两行合起来 |
| 特殊情形可求最优 | 入树（in-tree，出树经时间反演同理）、单位时长：“最高层优先”最优（Hu 1961，Oper. Res. 9(6)）；2 台机器、单位时长：Coffman–Graham 1972 最优（更早有 Fujii–Kasami–Ninomiya 1969）；固定台数、单位时长：(1+ε) 近似，Levey–Rothvoss 2016 的时间略高于准多项式（n^{(log n)^{O(log log n)}}），Garg 2018 降到准多项式 | — |
| 在线 | 两种模型要分开：(a) 任务在前驱完成时才出现（图事先未知）：即使单位时长，确定性算法下界 2 − 1/m，随机算法下界 2 − 2/(m+1)（Epstein 2000，IPL 76）；(b) 图已知、只是耗时未知：确定性下界 2 − 1/m 由一个简单的对手构造即得（常归于 Shmoys–Wein–Williamson 1995，未核对原文）。两种模型里贪心的 2 − 1/m 都能达到 | Graham；Epstein 2000 |
| 实用上最好的启发式 | **关键路径优先**（HLFET：按“到终点的剩余最长路径”排序）。Adam–Chandy–Dickson 在 900 多次模拟（随机图 20–266 个节点、22 张真实程序的图、2–10 台处理机）里，HLFET 除一个情形（一张真实程序的图，16.1%）外都不超过最优 4.4%；确定性情形的“最优”是用 Fernandez–Bussell 下界代替的，HLFET 平均只比它高 0.12%–0.22%。**只按图结构定层次的 HLFNET 平均比下界高约 6.3%–6.5%** | Adam–Chandy–Dickson 1974（CACM 17(12)，第 686、689 页，表 I） |
| 运行时调度的同型结果 | Brent 定理：T_P ≤ T_1/P + T_∞（原文是 t + (q − t)/p 的形式，更紧）；work stealing 对 fully strict 计算的期望时间 T_1/P + O(T_∞) | Brent 1974（JACM 21(2)）；Blumofe–Leiserson 1999（JACM 46(5)） |

要点：这是一个被研究了六十年的问题。“最优算法”在一般情形不存在（NP 难），但贪心离最优有界、关键路径优先在实践中接近最优，而且**差距的上限由 x 决定**（第 2 节）。【实测】我们自己的数据与 1974 年的结论一致：在 89 个证明了最优的 40–250 模块子图上，关键路径优先平均离最优 0.5%–1.1%，最坏 3.9%；在整个 Mathlib 上离 Fernandez–Bussell 下界不到 0.5%；合成工程 2,613 个模块 4 核时 CP-SAT 证明最优 383.1 秒，关键路径优先 383.3 秒。

### 3.1 带通信延迟（“空间上怎么切”的理论）

- 加上通信延迟后问题更难：单位时长、单位延迟、有限台处理机就是 NP 完全的（Rayward-Smith 1987，DAM 18）；即使处理机无限多也难：P∞|prec, p=1, c=1|C_max 好于 7/6 是 NP 难的（Hoogeveen–Lenstra–Veltman 1994），已知 4/3 近似（Munier–König）。Papadimitriou–Yannakakis 1990（SICOMP 19(2)）的 2 倍近似是**允许任务复制**的情形；不复制时没有已知的 2 倍近似，他们声称的 2 倍难度也未被证明（Kulkarni–Li–Tarnawski–Ye 2020 指出）。
- 两类算法：
  - **先聚类再调度**：把图切成簇，簇内不付通信。Sarkar 的边归零（1989）、线性聚类（Kim–Browne 1988）、DSC（Yang–Gerasoulis 1994）。这就是“先把仓库切成几块、每台机器建一块”的理论形态。
  - **带通信的列表调度**：ETF（最早开始时间优先，Hwang–Chow–Anger–Lee 1989，SICOMP 18(2)：在不考虑网络争用时 ≤ (2 − 1/C)·无通信最优 + 一条链上的通信总和）、DLS、HEFT（异构机器，Topcuoglu 等 2002）。集群系统里对应的是“延迟调度”（Zaharia 等 2010，Spark 的 `spark.locality.wait`）：数据所在的机器很快会空出来时，宁可等它。
- **粒度定理**（Gerasoulis–Yang 1993，IEEE TPDS 4(6)；原文未取到，按作者的 DSC 技术报告 UCSB TR 1994-12 第 5.1 节）：对每个节点 x，取它的后继中最小的任务时长 ÷ 它出边上最大的通信量，以及前驱与入边上的同一比值，二者取小得 g_x；图的粒度 g(G) = min_x g_x，g(G) ≥ 1 叫粗粒度。定理：**任何**线性聚类的并行时间 ≤ (1 + 1/g(G))·最优（对任意 g 成立，粗粒度时即 ≤ 2 倍），且粗粒度图存在最优的线性聚类。注意这里的“最优”是**处理机无限多、不复制任务**时的最优，并不直接说明 C 个核上的情形。
- **对我们**：任务时长是 0.2 秒到几百秒；通信是内网 0.2 毫秒延迟加每秒约 1 GB，本机实测每个任务在编译之外的开销中位数 4 毫秒。g 在几十到十万之间，属于极粗粒度。**理论的结论是：在这种参数下不应该预先切分，谁空谁领的动态贪心就接近最优；预先切分只会丢掉 Graham 的保证**（一台机器空着、另一台排着队）。【模拟】T3 把粒度一直扫到 g = 0.1：g ≥ 10 时放置毫无影响；g ≈ 3 以下必须按数据所在动态派（ETF 或 EST + 延迟调度）；**但到 g = 0.1 为止，先聚类再调度（线性聚类、按目录、沿导入链）从没赢过看数据的动态派发**（有限台机器上丢掉的负载均衡比省下的通信多）。带宽极低、只按需拉取产物时聚类可能有用，这一情形还没建模。

### 3.2 可塑任务（一个文件给几个线程）

- 带先后约束的可塑任务调度有常数倍近似：Lepère–Trystram–Woeginger 2002（IJFCS 13(4)）3 + √5 ≈ 5.236（假设核数增加时耗时不增、总工作量不减）；Jansen–Zhang 2006（ACM TALG 2(3)）约 4.7306（同样假设）；Jansen–Zhang 2012（JCSS 78(1)）约 3.2919（加速函数凹）；Chen–Chu 2013（IEEE TPDS）2 + √2 ≈ 3.414（另加“工作量是时间的凸函数”）。Chen 2026 的预印本（arXiv 2611.15111，未经同行评议）认为 Chen–Chu 文中更好的 2.9549 不成立，并给出约 3.016 与 2.974。所以是“3.3 左右”，不是“3 左右”。通用做法分两步：先给每个任务定核数（时间与工作量的折中，线性规划加舍入），再做列表调度。
- 实用规则：Isabelle 的新排程（Huch–Wenzel 2024）按 session 的长度给线程（1 分钟以内 1 线程、5 分钟以内 4 线程、更长 8 线程，有空闲核时再多给），并把关键 session 给最快的机器。核数紧张（x < 1）时多给线程是净损失，因为多线程的总工作量更大。【实测】Mathlib 的重文件 2 线程加速 1.44 倍、8 线程只有 1.47 倍，2 线程就饱和；“空核分享、每文件最多 2 线程”在 128 核以上把 Mathlib 从约 20 分钟压到约 14 分钟（`docs/study-report.md` 3.5 节）。

## 4 真实系统是怎么调度的

| 系统 | 做法 | 用没用关键路径 |
|---|---|---|
| make -j | 拓扑序，就绪就跑，不排优先级 [S36] | 没有 |
| Ninja | 就绪队列；1.12.0（2024-04，PR #2177）起始终按“关键路径”排优先级，但每条边权重都是 1，即按剩余**层数**而不是耗时；按 `.ninja_log` 耗时加权的 PR #2686 2026-09 才并入 master，截至 1.13.2 尚未发布 | 有，但只按图深度 [S9] |
| Bazel / Buck2 | 动作图，就绪就派。Bazel 本地动作在 `ResourceManager` 里先进先出（动态执行时后进先出），远程优先级是用户设的一个整数（`--remote_execution_priority`）；关键路径（`CriticalPathComputer`）只用于事后报告。Buck2 本地动作排一个公平信号量，`priority` 只传给远程执行服务；关键路径进 build signals 用于报告 [S10][S14] | 没有（只事后报告） |
| Lake | Lean 的任务（`Task`），都是默认优先级（`Lake/Build/Job/Monad.lean`，v4.35.0），没有耗时或关键路径的逻辑 [S6] | 没有 |
| Isabelle 集群构建 | 经典引擎：按上次构建的耗时，“后继路径上耗时最长的 session”先跑；2024 年的新引擎（`build_schedule`，需显式开启，默认仍是经典引擎）把问题当作多模式资源受限项目调度，用并行的排程生成启发式，路径长于阈值（10–20 分钟效果好）的“关键 session”给最快的机器，线程按 session 长度给，默认每 5 分钟重排；在较短的构建上经典引擎仍更快，在 AFP 上新引擎省 7–8 分钟（35 分 40 秒）[S32] | 有 |
| Cilk、TBB 等运行时 | work stealing | 不显式用，但有 T_1/P + O(T_∞) 的保证 |
| Spark / Dask | Spark：阶段图，延迟调度（`spark.locality.wait`）保证数据就近。Dask：`dask.order` 的静态排序以节省内存为主，其中的“关键路径”只按结构、不按耗时加权；分布式调度器再按“计算与传输的代价”做 work stealing [S33][S34] | 部分（Dask 只按结构） |
| 科学工作流（Pegasus 等） | HEFT 是可选的站点选择器，默认是随机 [S35] | 可选 |
| 研究系统 | Graphene（OSDI 2016，依赖感知加多资源装箱）、Decima（SIGCOMM 2019，用强化学习学调度策略） | 有 |

共同点：工业界的构建系统几乎都是贪心，差别只在“排不排关键路径”和“管不管数据位置”。**主流构建系统里真正按耗时排关键路径的几乎没有**：Ninja 已发布的版本只按层数，Bazel、Buck2、Lake、make 都不排；只有 Isabelle 按历史耗时排。没有系统去解最优化问题，因为第 3 节说明了那不划算。

## 5 到目前为止的模拟结论

指标是“时长 ÷ 下界 max(W/C, CP)”，越接近 1 越好。两份 trace 的 W/CP 都只有约 5。

**规则比较**（单线程任务；**更正**：这张表来自每任务 0.1 秒开销的运行，不是零开销；零开销、单池的完整锦标赛见 `docs/study-report.md` 3.4 节）：

| 230 模块真实工程 | 4 | 0.80 | 1.012 | 1.179 | 1.334 |

| | 16 | 3.2 | 1.004 | 1.019 | 1.051 |

| 2,613 模块合成工程 | 4 | 0.80 | 1.504 | 1.732 | 1.734 |
| | 16 | 3.2 | 1.114 | 1.219 | 1.233 |
| | 32 | 6.4 | 1.041 | 1.092 | 1.096 |
| | ≥128 | ≥26 | 1.041 | 1.041 | 1.041 |

1. 与第 2 节一致：差别只出现在拐点附近，关键路径优先比不排优先级快 10%–25%；远离拐点时所有规则相同。
2. 合成工程在 4 核上离下界 1.5 倍：其中约 0.17 是 0.1 秒开销本身（这个工程的模块平均只有 0.44 秒）；零开销时是 1.33 倍，而 **CP-SAT 证明这就是最优**（最优 383.1 秒，关键路径优先 383.3 秒；简单下界 287.6 秒，Fernandez–Bussell 下界 322.5 秒）。所以差距全在下界，调度本身已经最优。

**耗时估计不准**（合成工程，16 核）：动态派发在各种估计误差下都是 1.114–1.126；完全不知道耗时、只按图结构算剩余链长，也是 1.115。预先算好的静态计划从 1.114 退化到 1.34。**更正**：“优先级只需要图的结构”只在模块耗时均匀时成立（合成工程正是如此）。在拐点附近，只按结构排在 Mathlib 上慢 5.8%，在黎曼猜想归档的模型上慢 17%，在 230 模块工程（一个文件占最长链 77%）上慢 37%；Adam–Chandy–Dickson 1974 的 HLFNET 也是平均高出下界 6.3%–6.5%。正确的结论是：**优先级要用耗时，但粗略的就够**——Mathlib 上只按行数估只慢 0.7%（`docs/study-report.md` 3.6 节）。耗时估计的主要价值仍在预估资源。

**任务粒度**（合成工程，模块耗时中位数 0.36 秒）：零开销时，按单个模块派发是 1.00；每 5 个模块一批是 1.09（批内建完一个放行一个）到 1.22（整批建完才放行）；每 20 个一批是 1.26 到 1.61；每 60 个一批是 1.73 到 2.07。每个任务有 1 秒固定开销时，单模块派发变成 1.41，5 个一批是 1.20。结论：**批次只有在“每个任务的固定开销大于典型模块耗时”时才划算**；我们实测的固定开销是 4 毫秒，所以不该分批。“链收缩”（只有一个上游和一个下游的相邻模块合并）不损失并行度，可以免费做。

## 6 所以，收益从哪里来

把第 2、3、5 节合起来，一个仓库在 C 个核上的构建时间大约是 W/C + CP 的量级，可动的只有三项：

1. **别偏离贪心**。预先切块、整批放行、静态计划加不准的估计，都会让机器空等。这是最容易丢、也最容易拿回的一块（模拟里 20%–100%）。
2. **在拐点附近用关键路径优先**。最多 10%–25%，而且只需要图结构。
3. **改变 W 和 CP 本身**。x ≫ 1 时唯一有效的手段：缩短关键路径（拆开链上的重文件、给它多线程、去掉语义上不需要的 import），以及用缓存减少 W。这部分没有上限，是真正决定“大集群上能快多少”的地方。

调度算法之间的差别有界（最多一倍，实际一两成），而仓库结构决定的上限差别是数量级的（Mathlib 实测 36.6，黎曼猜想归档按模型约 510–536，一个 230 模块的工程只有 5）。

## 7 接下来按理论做的探索

| 编号 | 问题 | 做法 | 能得到什么 |
|---|---|---|---|
| T1 | 我们离最优到底多远 | 实现 Fernandez–Bussell 下界；对几百个任务以内的子图用整数规划或约束求解器求真正的最优 | 最优性差距的实数；如果只剩百分之几，就不必再找更好的调度算法 |
| T2 | 拐点附近哪个规则最好 | 关键路径优先的几个变体（剩余最长链、加权后继数、带前瞻）、ETF、以及对优先级表做局部搜索的“近似最优”；在 Mathlib、黎曼猜想归档上按 x 从 0.1 到 10 扫 | 一张“规则 × x”的表和推荐的默认规则 |
| T3 | 什么时候该切分 | 按粒度 g 扫通信延迟与带宽，比较动态 ETF、延迟调度、DSC 聚类、按目录切 | g 的临界值：低于它才值得聚类 |
| T4 | 线程怎么给 | 实测重文件的加速曲线 p_v(k)；比较“空闲核给关键路径”与两步法 | 线程分配规则，以及它能把 CP 缩短多少 |
| T5 | 结构上能把上限提高多少 | 关键路径上的文件逐个分析：拆分、多线程、去掉不需要的 import 各能减多少 | 每个仓库“加速比上限”的可提升空间 |
| T6 | 模型准不准 | 用三台机器的实测（实验 E1、E2）对比模拟预测 | 预测误差；之后才外推到大集群 |

## 8 思想实验：先想清楚会看到什么，再去测

**相似律。** 第 2、3 节说明，构建时间的形状只由几个无量纲的数决定，与机器的绝对规模无关：

- x = C·CP / W：核数相对仓库可并行度的比例；
- g = 任务时长 ÷ 通信时间：粒度；
- p：重文件里能并行的部分（决定多线程能把 CP 缩短多少）。

所以“用弱环境模拟强环境”有确切的含义：**小集群上取到和大集群相同的 x 和 g，结论就能搬过去**。黎曼猜想归档（W/CP ≈ 400）在 400 核上是 x ≈ 1；一个 W/CP ≈ 60 的仓库在 48 核上是 x ≈ 0.8，是同一种情形。x 靠改变每台机器给的核数来扫，g 靠人为加传输延迟来扫。

**实验设计。** 两个实例，同一套代码，同一个公式给预测：

| 实例 | W/CP | 作用 |
|---|---:|---|
| 宽图（合成，结构取自黎曼猜想归档的子闭包） | ≥ 60 | 正例：多机应当接近线性 |
| 窄图（已有的 2,613 模块合成工程） | 约 5 | 反例：多机应当几乎没有收益 |

**预测**（T ≈ r(x)·max(W/C, CP)，r 取模拟里关键路径优先的典型值；“三机加速比”是单机 c 核对三机各 c 核）：

| 实例 | 每台核数 c | 单机的 x | 三机的 x | 预测的三机加速比 |
|---|---:|---:|---:|---:|
| 宽图 | 4 | 0.07 | 0.2 | 2.9 |
| 宽图 | 8 | 0.13 | 0.4 | 2.7–2.8 |
| 宽图 | 16 | 0.27 | 0.8 | 2.2–2.6 |
| 窄图 | 4 | 0.8 | 2.4 | 1.3–1.5 |
| 窄图 | 16 | 3.2 | 9.6 | 1.0–1.1 |

另外四条预测：

1. 宽图、三机各 16 核（x ≈ 0.8，在拐点上）：关键路径优先比“先就绪先派”快 10%–25%；每台 4 核（x ≈ 0.2）时两者相差不到 5%。
2. 预先切块（每台机器固定建自己那一块）比动态派发慢，按目录切慢得多（20% 以上），沿依赖链均衡切也追不上动态派发。
3. 人为把每次跨机取产物的延迟加到与模块耗时同量级（g ≈ 1）之前，动态派发始终不输给聚类；到 g ≲ 1 才反转。
4. 只用图结构排优先级，与用真实耗时排，结果相差不到 2%。

**研究会话的模拟预测**（`docs/study-report.md` 4.2 节，宽图用的是从黎曼猜想归档切出的代理，真实实例出来后重算）：窄图三机 ÷ 单机加速比 1.54 / 1.24 / 1.06（每台 4 / 8 / 16 核，5%–95% 区间 1.41–1.65 / 1.20–1.32 / 1.05–1.09）；宽图 2.87–2.98 / 2.66–2.96 / 2.37–2.93。宽图三机各 16 核时关键路径优先比先就绪先派快 9%–22%，各 4 核时 1%–6%。预测 3 与模拟不符：到 g = 0.1 为止动态派发都没输给聚类。预测 4 只对耗时均匀的图成立（见第 5 节更正）。

**什么结果说明我错了**：宽图在 x ≤ 0.3 时三机加速比低于 2.5（说明有模型外的开销，要找出来）；窄图在 x ≥ 3 时加速比明显高于 1.2（说明 CP 估错了）；预先切块赢了动态派发（说明通信比我以为的贵）。

**工程只需要提供四样东西**：能设每个 worker 的核数；能切换派发规则（关键路径优先、先就绪先派、固定放置）；能人为加传输延迟；逐模块的运行记录。这些在现有代码里都有或只差很小的改动。


## 附：文献核对与修改记录（研究会话，2026-11-25）

核对方法：逐条找原文（论文全文或作者的技术报告、官方文档、发行说明、源代码）；读不到原文的已注明。改动：

1. 第 2 节：Fernandez–Bussell 下界写成准确的形式 T ≥ CP + max_θ(R(θ)/C − |θ|)；补上本研究的实测（它几乎是紧的）。Mathlib、黎曼猜想归档的 W/CP 与 x 改用实测值和模型值。
2. Ullman 1975：补“处理机数是输入的一部分”；固定 m ≥ 3 是否 NP 难仍未解决。
3. Svensson 2010：写明假设是 Bansal–Khot 的唯一博弈猜想变体、单位时长即成立、m 是输入的一部分；“贪心已是能证明的最好”因此是有条件的。
4. Hu 1961：是入树（出树经时间反演）；Coffman–Graham 之前有 Fujii–Kasami–Ninomiya 1969。
5. Levey–Rothvoss 2016：时间略高于准多项式；真正准多项式的是 Garg 2018。原文“拟多项式”改为“准多项式”（拟多项式通常指 pseudo-polynomial）。
6. 在线：Epstein 2000 的模型是“前驱完成时任务才出现”（图未知），下界确定性 2 − 1/m、随机 2 − 2/(m+1)；与“图已知、耗时未知”的模型分开写。
7. **Adam–Chandy–Dickson 1974**：原文的“5%”是他们事先定义的“接近最优”的门槛，不是结果；结果是“除一个情形外都不超过 4.4%”，确定性情形的“最优”是 Fernandez–Bussell 下界，HLFET 平均只高 0.12%–0.22%；只按结构的 HLFNET 高约 6.3%–6.5%。
8. Brent：原文形式更紧；Blumofe–Leiserson：限 fully strict 计算。
9. **Papadimitriou–Yannakakis 1990**：2 倍近似要求任务复制；补上无限处理机、不复制时的结果（7/6 难度，4/3 近似）。
10. ETF 的界补“不考虑网络争用”；延迟调度标明是 Spark 的机制。
11. Gerasoulis–Yang 1993：写出粒度的准确定义；定理对任意 g 成立（粗粒度时 ≤ 2 倍）；“最优”是无限处理机下的，不直接适用于 C 个核。原文未取到，依据作者的技术报告。
12. 可塑任务：近似比与假设逐条写准；“降到 3 左右”改为“3.3 左右”，并注明 2026 年预印本的争议。
13. 第 4 节：Ninja（只按层数，耗时加权尚未发布）、Bazel / Buck2（不排，只报告）、Lake（默认优先级）、Isabelle（新引擎需显式开启、线程按长度、关键 session 给快机器、在较短构建上经典引擎更快）、Dask（静态排序按结构、work stealing 按代价；延迟调度是 Spark 的）、Pegasus（HEFT 可选，默认随机）。
