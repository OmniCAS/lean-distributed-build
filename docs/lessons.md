# 实践经验：在真实机器上做多机构建学到的东西

2026-11-24 至 11-25，三台共用的 64 核服务器（下称 worker-1、worker-2、worker-3），一台笔记本作控制端，经跳板机连入。每条按“现象 → 原因 → 对策”写，只写有实测或记录支撑的；原因不清楚的写“原因未查明”。数据位置写在每条末尾。

## 1 产物里有源码的绝对路径

- **现象**：同一模块在不同目录下编译，带警告的模块 `.olean` 不同，其余逐字节相同（本机原型：恰好那 32 个带警告的模块不同，`.ilean` 全同）。黎曼猜想归档里 175,187 个 `.olean` 中 98,219 个嵌了路径 [D1][D8]。
- **原因**：Lean 4.33 起把 linter 消息连同源文件绝对路径存进产物。
- **对策**：所有机器用同一个绝对目录放源码和工具链（E1 三台都用同一路径）；逐字节比对作为验收的一部分。照此做，宽图三机产物与单机原版 `lake build` 12,999 / 12,999 个文件一致，中图 9,468 / 9,468 一致（实测，`bench/results/`）。需要与路径无关的比较时比导出哈希 [D8]。

## 2 机器连不上外网时，工具链与依赖怎么到位

- **现象**：三台都连不上 GitHub 的发布资产（release 下载地址不通）；控制端经跳板机向服务器上传只有约 11 KB/s，跳板机自己下载 GitHub 约 30 KB/s，都不可用；`git clone` 经 HTTPS 极慢，并在 HTTP/2 下中途断流（`RPC 失败 … HTTP2 framing layer`）；GitHub 的源码包下载（codeload）可用，约 450 KB/s（另一次前几分钟只有约 40 KB/s，后来变快）。可用的代理：一个要认证；另一台机器上配置过一个代理，但从 worker-2 到它没有路由，最后都没用上。
- **原因**：网络策略，原因未查明。
- **对策**（都做过，实测有效）：
  1. **工具链**：在已经装有官方工具链的机器上找到需要的版本，先把关键文件（`bin/lean`、`bin/lake`、`libleanshared.so`）的 sha256 与官方发布包逐个核对，再经 10 GbE 用一次性 TCP 直传到其他机器（3.08 GB、20 秒，两端 sha256 一致）。因为只有 v4.34.0 可用，Mathlib 也改用 v4.34.0（而不是计划里的 v4.35.0），预测与实测都按这个版本。
  2. **源码与依赖**：用源码包而不用 `git clone`；按 `lake-manifest.json` 的提交号逐个取依赖的源码包，解包后提交成本地快照（`origin` 设为原地址），manifest 改指快照提交——Lake 从此离线加载工作区，不再联网（`study/scripts/remote/setup_tarballs.py`）。源码包的 sha256 与控制端直接下载的一致。
  3. **一台准备好、整份分发**：Mathlib 与依赖在一台上准备好后，整份检出经 10 GbE 拷到另两台的同一路径，三台的依赖构建摘要一致（记录见 `progress.md` 11-25 的 E2 准备）。
  4. 有一台机器上对另一台的 SSH 主机密钥记录已过期；我们没有去改它，传输改用上面的一次性 TCP 直传。

## 3 服务器上的 Python 旧

- **现象**：worker 端是 Python 3.10，没有 `tomllib`（3.11 才有），工具读 `lakefile.toml` 失败；一台机器上没有 uv。
- **对策**：协调器在自己那边解析好配置，连同任务一起发给 worker（worker 不再读 TOML）；生成实例的脚本保持 Python 3.8 可用。

## 4 机器快慢不同，预测要按实测速度

- **现象**：同一模块在 worker-2 上慢 1.29–1.44 倍、worker-3 上慢 1.07–1.13 倍（相对 worker-1；worker-2 构建前的负载就有 11–15）。只用单机参照时长、当三台一样快做的“运行前预测”，中图低估 21%、宽图低估 27%（实测 vs 模拟，`study/t6_calibrate.py`）。中图三机运行的最长链上 35 个模块有 22 个落在两台慢机器上，比参照最长链多出 50 秒。按 CPU 主频估的速度比（1.06 倍）与实测（1.44 倍）差得很远。
- **原因**：派发是“谁先来领就给谁”，不看机器快慢；机器与别人共用。
- **对策**：每次大构建前在每台 worker 上用同一组模块测一次速度，写进计划；按实测速度、开工时刻和每任务开销预测后，9 次运行的误差在 −7.0% 到 +7.7%（`bench/expected.md`）。调度上应把关键模块派给快机器（模拟：“最早完成”放置省 2%–10%，未实测）。
- **速度会变**：两机那批（11-25）worker-2 只慢 1.13–1.29 倍（多数运行 1.16–1.19），不再是校准时的 1.44 倍；两批运行前后记录的系统负载相近，变快的原因不明。沿用上一批的速度，单机格的预测高估 16%–20%，18 格里 8 格出了容差；按每次运行自己量出的速度重算，宽图不加延迟的 11 格误差 −8.4% 到 +4.1%（`study/e1_two_machines.py --recalibrate`）。所以速度不能沿用上一批，每次运行前都要量。

## 5 Lake 给每个编译进程开满线程

- **现象**：16 个核上同时跑 16 个 Mathlib 文件时，每个 `lean` 开 16 线程（`lake build` 在 `LEAN_NUM_THREADS=16` 时的做法）比 1 线程多用 25% 的 CPU、各模块墙钟之和多 19%（实测，32 个文件直接对照，`study/data/runs/replay/waves.jsonl`）。同一文件单独用 1 线程比它在原构建里快 14%。在 E1 的合成模块上没有差别（1.02 倍），因为它们关掉了文件内的并行 elaboration。
- **原因**：Lake 的任务池大小和每个子进程 `lean` 的线程数都取 `LEAN_NUM_THREADS`；核已经占满时，文件内的并行只带来开销。另外，Lake 在一百多个线程以上会卡在自己的锁上（192 核机器上只能降到 64 线程 [D1]；288 核上同时只有 7–47 个 `lean` 在跑 [D11]）。
- **对策**：核紧张时每个 `lean` 1 线程、槽位数 = 核数；只在有空核时给到 2 线程（2 线程已饱和：1.44 倍，8 线程 1.47 倍，实测）。

## 6 每任务开销与 worker 启动时间

- **现象**（中图三机，实测最长链的精确分解，共 419.4 秒）：编译 382.7 秒，每任务开销（取产物、上传、启动 `lean`）23.4 秒（5.6%），开头等 worker 13.1 秒（3.1%），派发与放行 0.2 秒。三个 worker 在协调器启动后 13.0、22.4、29.3 秒才开工。宽图三机：协调器启动到第一个模块开工 15.7 秒；之后槽位 80% 的时间在跑 `lean`，有就绪模块却空着的 3.5%，没有就绪模块的 4.9%，每个模块上传约 0.17 秒（`study/results/t6-*.json`、`progress.md`）。
- **原因**：开工晚主要是实验脚本经跳板机逐台 SSH 起 worker，不是工具本身；扣掉这段，宽图三机对单机是 2.36 倍（实测 2.27 倍）。
- **对策**：worker 提前起好、或并行地起；上传与下一个任务重叠。另外，单机运行里出现过一次协调器停顿：16 个模块 19–29 秒建完，77 秒才放行，其间 16 个槽位全空约 47 秒（实测），原因未查明，要在工具里加监控。

## 8 挑实例的脚本把最长链低估了 2.3 倍

- **现象**：第一个合成实例按挑选脚本算的可并行度约 67，实测只有约 32。
- **原因**：脚本假设导入图文件里的模块编号是拓扑序，算最长链时漏掉了还没访问到的 import，把最长链低估 2.3 倍。
- **对策**：最长链一律先显式求拓扑序再算；在已知答案的小图上测；正式实验前先跑一次单机参照，用实测的 W/CP 核对挑选时的估计。那个实例改称“中图”继续用（实测 W/CP 31.7），修正后重挑出“宽图”（挑选时 62，实测 59.5–60.5）。

## 9 共用机器上的计时起伏

- **现象**：同一台机器上两次运行，同一模块耗时的对数标准差 0.11–0.14；最慢那台 0.13–0.22（实测，E1 记录）。本工具单机跑中图那次，机器负载被别人的进程推到 42，结果 773 秒，比原版 Lake 的 733 秒还慢。Mathlib 全量构建期间其余 CPU 平均约 7 个核被别人占着。受最长链限制的运行，同一配置在模拟里 10 次的范围是 390–502 秒（±15%）。
- **对策**：每次运行前后记录各机器负载（`meta.json` 里有）；绑核（`taskset`）、降优先级（`nice -n 10`）、避开别人常用的核；每格重复三次取中位数；比较时多用比值；预测带至少 ±15% 的容差。

## 10 一台机器的根文件系统变成只读（11-25）

经过（事实陈述）：

- worker-1 当地时间约 15:45，协调器写运行记录时报 `OSError: [Errno 30] Read-only file system`。
- 此后新的 SSH 会话一登录就被结束（经跳板机、经另一台 worker 两条路都一样）；这台机器仍能 ping 通（约 0.2 毫秒）。
- 正在跑的运行（宽图、沿导入链固定放置）停在 2,047 / 4,333 个模块，结果作废。
- 另两台上的 worker 与 `lean` 进程已停掉；worker-1 上的协调器与 worker 进程停不掉（无法登录），留在它的临时目录里。
- 当时另两台的根盘：一台 83%（我们的目录占 25 GB），一台 24%（26 GB）。
- 已收回控制端的数据不受影响（中图 3 次、宽图 6 次运行的记录都在）。
- 处理：worker-1 上的实验停了，等管理员处理那台机器；我们没有 sudo，不改系统配置。随后改在另外两台上继续（两机队列，预测见 `bench/expected.md` 的“两台机器”一节）。

原因（11-25 当天查明，来自那台机器的内核日志，只读检查得到）：

- **根盘的 NVMe 在多轮 I/O 超时后被内核移除**。当天下午约两小时前出现过一轮超时、控制器复位后恢复；出事前几分钟超时越来越密，三次控制器复位，几个进程在文件系统读写上卡住超过 120 秒，随后内核禁用控制器，根文件系统所在设备出现大量写入错误，内核以“探测失败”把这块盘移除。内核日志到此为止；约五分钟后我们发现根文件系统只读。
- **同一块盘在十天前就出现过同类 I/O 超时**（当时自行恢复），那时我们在这台机器上还没有做任何实验或改动。
- 机器没有重启过（启动标识未变），网络正常；SSH 能完成认证，但会话一建立就被结束，执行不了任何命令。
- 出事当天，这块盘上的写入除了别人的服务，还有我们的构建实验（协调器与 16 个编译进程的临时目录）和另一条线迁来的运行数据。**负载是否加速了这次掉线，现有记录不足以判断。**

经验：

- **每次运行结束马上把记录收回控制端**——这次正是这样才没丢数据。
- **协调器与产物库所在的机器是单点**：它出事，正在跑的运行就丢了。设计上协调器不保存状态、进度以产物库为准（`docs/problem-and-roadmap.md` 第 6.2 节），但产物库本身也在那台机器上。之后应把产物库放在协调器以外的地方，或者能从各 worker 本地的产物恢复。
- **临时目录要及时清**：一台机器的根盘到了 83%，其中 25 GB 是我们的运行目录。
- **在共用的旧机器上做 I/O 密集的实验前，先看一眼内核日志里有没有磁盘超时的历史**（例如 NVMe 的 I/O timeout、controller reset）。这次的盘十天前就有记录；事先看到的话，我们会把协调器、产物库和大量临时写入放到别的机器上。

## 11 派发不看数据在哪，取件一慢就输给固定切分

- **现象**：两机宽图上，让每个要从另一台取导入的任务人为多等 X 秒。动态派发在 0.1 / 1 / 10 秒时 370 / 406 / 894 秒（不加延迟 359 秒）；按目录固定切分在 1 / 10 秒时 440 / 580 秒（不加延迟 423 秒）。10 秒时固定切分快 35%。动态派发有 1,441–1,557 个任务要跨机取件，共 6.1 GB；固定切分只有 159–198 个，3.2–3.5 GB，因为第二台机器那一块从不导入第一台上建的模块（实测，`bench/results/runs/wide2-*`）。
- **原因**：worker 谁来领，就把最高优先级的就绪模块给谁，开工时才去取缺的产物；每个这样的任务付一次延迟，并占着槽位。模拟器原来假定产物建完就推给所有机器、派发看数据所在，所以预测 1 秒几乎无影响，10 秒那格低估 41%。补上“按需拉取、不看位置”后，8 格回测误差 −9.9% 到 +0.1%，取件任务数也对得上（`study/e1_delay_backtest.py`）。原先“预先切块一直到传输比模块慢 10 倍都没赢过动态派发”只对看数据所在、产物推送的派发成立。
- **对策**：产物建完就推给其他机器（预取）；派发时为已有导入产物的机器等一会（延迟调度）。模拟：1 秒延迟 409 → 359 秒，10 秒 861 → 467 秒，按目录固定切分是 518 秒。只挑“最早能开工的机器”没用，因为两台都满时空出来的槽只在一台上。补上之前，取件慢（≥ 1 秒）的环境里按目录切块是可用的退路。我们的内网上每次取件实际约 0.07 秒（中位数），不影响现在的结果。

## 12 原版 Lake 加转发：经共享盘读依赖，在途任务上不去

- **现象**：用原版 Lake 调度，只把 `lean` 命令转发到两台机器执行（构建目录在共享盘 NFS 上，允许 32 个在途）。宽图用了 909 秒，比本工具两机的 359 秒慢 2.5 倍，比本工具单机的 671 秒还慢 35%。逐项看：同一模块的 `lean` 中位数多约 1 秒；超过 1 秒的模块中位数慢 1.48 倍；总工作量 14,551 对 9,447 核·秒，多 54%。平均只有 17 个 `lean` 同时在跑，30 个以上的时间只占 1.2%。等 NFS 上文件可见的时间中位数 0.02 秒，可以忽略（实测，`bench/results/runs/wide2-B5-c16-r1`，与 `wide2-B1-c16-r1` 逐模块对照）。
- **原因**：每个 `lean` 要经共享盘读整个导入闭包的 `.olean`，比读本地盘慢；Lake 自己也在共享盘上算哈希、写 trace，在途命令上不去（这一条没有单独量）。
- **对策**：不要让多台机器共用共享盘上的构建目录；每台用本地盘，产物经产物库复制过去（本工具的做法）。“保留 Lake 调度、只换执行端”这条路在我们的环境里不划算。

## 13 其他

- **一台机器不接受别的机器连入的端口**：所以协调器与产物库只能放在另外两台上，worker 一律只向外连（工具本来就是这样设计的）。
- **运行目录要唯一命名**：有一次远端运行目录沿用了旧名，宽图的单机参照覆盖了中图的参照产物（中图的逐模块耗时已在控制端，没丢），中图与 `lake build` 的逐字节比对改在宽图上做。
- **共享文件系统有 2–7 秒的短暂卡顿，且与几十个用户共用**（基础设施摸底）：所以构建目录放各机本地盘，机器之间只经产物库传产物；共享盘只在“原版 Lake + 只转发 `lean`”的对照组里用。
- **同一份数据在不同会话里的机器编号要统一**：E1 的记录与研究报告一度用了两套编号，已统一成 E1 记录的那套。
