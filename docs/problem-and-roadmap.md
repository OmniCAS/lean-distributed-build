## 1 问题定义

### 1.1 一句话

给一个 Lean 仓库和一组机器，尽快产出这个仓库的**构建缓存**，使任何人拿到缓存后不必再编译。

### 1.2 输入、输出

| | 内容 |
|---|---|
| 输入 | 仓库（Git 链接加提交号，或本地路径）；它的依赖（如 Mathlib，由仓库的清单文件锁定版本）；一组机器（每台的核数、内存、本地盘、网络） |
| 输出 1 | 构建缓存：每个模块的编译产物（`.olean`、`.ilean`、`.c` 等），按内容哈希存放，加一张清单（仓库、提交号、工具链、依赖版本、模块 → 文件） |
| 输出 2 | 运行报告：总用时、每个模块在哪台机器上建、起止时间、CPU、内存、失败与重试 |
| 消费方式 | 别人检出同一提交，执行“恢复缓存”，然后原版 `lake build` 报告全部已是最新 |

### 1.3 目标与约束

- **目标**：最小化从输入到输出的墙钟时间；同样的输入再来一次时，只做变化的部分（复用）。
- **正确性约束**：产物必须和单机原版 `lake build` 的产物等价（最好逐字节相同）；最终由 Lean 内核复核。逐字节核对排除原版 Lean 自己不可复现的模块：用原版 `lean` 按同一条命令编两次结果就不同的，单独列出（Mathlib v4.34.0 里有 1 个，见 `docs/lessons.md` 第 15 节）。
- **安全约束**：编译会执行仓库里的元程序，第三方仓库只能在隔离环境里建；缓存分“未复核”和“已复核”。
- **资源约束**：每个编译进程要把它依赖的全部产物映射进内存；机器可能与别人共用、快慢不一。

### 1.4 不在范围内

- 不改 Lean 编译器本身，不改仓库源码（“拆文件、删 import”只作为分析结论给出）。
- 不负责证明的数学正确性，只负责“构建产物与单机一致，并经内核复核”。

### 1.5 术语

| 术语 | 含义 |
|---|---|
| 模块 | 一个 `.lean` 文件，编译的最小单位 |
| 导入闭包 | 一个模块直接或间接 import 的全部模块；编译它时这些模块的产物都要在场 |
| W（总工作量） | 所有模块单核编译时间之和 |
| CP（最长链） | 导入图上耗时之和最大的一条依赖链 |
| 可并行度 | W ÷ CP：加速比的上限 |
| x | 核数 × CP ÷ W：核数相对可并行度的比例，决定处在哪种情形 |
| 缓存键 | 一个模块全部输入的哈希；键相同则产物可复用 |

## 2 这是一个常见问题：业界的标准解法

“把构建分到多台机器并复用结果”在 C++、Java 的世界里是成熟技术，标准形态是**远程缓存 + 远程执行**。Lean 目前只有前一半。

### 2.1 已有系统（已按官方文档与源码核对，出处见编号）

| 系统 | 做法 | 与我们的关系 |
|---|---|---|
| distcc、icecream | 构建工具不变，用包装器替换编译器，逐个编译命令转发到远程。distcc 由客户端按主机列表选机器（普通模式本地预处理后发送，pump 模式连头文件一起发、远程预处理）；icecream 由中央调度器按机器快慢和空闲分配，并把编译器环境打包发过去 [S24][S25] | 对应“保留 Lake 调度，只转发 `lean`” |
| ccache、sccache | 按输入哈希缓存单次编译的输出（C/C++ 多为预处理结果 + 编译器与参数的哈希）；ccache 自身不分布，可串接 distcc；sccache 支持 S3、GCS、Redis、Azure 等多种远程存储，并有 sccache-dist（调度器 + Linux/FreeBSD 构建机，自动打包工具链）[S26][S27] | 对应缓存键与产物库 |
| Bazel、Buck2、Pants 的远程执行（Remote Execution API） | 每个动作 = 命令摘要 + 输入根目录树摘要；服务端由内容寻址存储、动作缓存、执行服务（调度 + worker）组成；先查动作缓存。协议有每个请求的 `ExecutionPolicy.priority`（默认 0，约定数值小的先跑，具体含义由服务端定）；Bazel 只有一个全局的 `--remote_execution_priority` [S16][S10][S13][S14][S15] | 最完整的参考架构 |
| Remote Execution API 的开源服务端 | Buildbarn、BuildGrid、Buildfarm、NativeLink 都可以自建；对优先级字段的解释不一：Buildbarn 在一次构建内严格按优先级、再按预计耗时长者先；BuildGrid 按升序并可对重复请求提升；Buildfarm 要打开 `priorityQueue` 才生效；NativeLink 反过来，数值大的先跑 [S17][S18][S19][S20] | 若架在这类集群上，关键路径要按各家的约定映射到优先级 |
| recc、reclient | 把单条编译命令包装成远程执行动作。recc 面向 C/C++，可显式指定输入（独立仓库已并入 buildbox）；reclient 是 Chromium 用过的客户端，2025 年起被 Siso 内置的客户端取代 [S21][S22][S23] | 对应“给 `lean` 命令套一层” |
| Nix 与 Hydra | 存储路径默认按输入寻址（按内容寻址的 derivation 仍是实验特性）；可经 SSH 配多台远程构建机；Hydra 是 Nix 的持续集成服务 [S28][S29] | Lean 4 早期有过每模块一个 derivation 的 Nix 构建（`buildLeanPackage`），2024-08 弃用，2025-08 移除 [S30] |
| Isabelle 的集群构建 | 证明助手里最成熟的：经典引擎按历史耗时“后继路径最长者先”；2024 年的新引擎（需显式开启）用启发式排程，关键 session 给最快的机器，线程按 session 长度给，默认每 5 分钟重排 [S32] | 调度策略的直接参考（AFP 单台高端服务器 4–8 小时，集群 35 分 40 秒 [S32]） |
| Lake 的产物缓存、Mathlib 的 `lake exe cache` | Lake 本地产物缓存（4.22 起）；远程缓存与 `lake cache`、`lake build -o`（4.25 起，4.30 大改：构建时按需下载、批量取地址、`.ltar` 打包）；Mathlib 的缓存键混合根哈希、文件路径、内容与各 import 的哈希，产物以 `.ltar` 存放 [S2][S3][S5][S8] | 我们的输出应与它兼容 |

### 2.2 标准架构的五个部件

1. **客户端**：分析构建图，为每个动作算输入哈希，先查缓存，未命中才提交执行。
2. **内容寻址存储**：所有文件按内容哈希存一份。
3. **动作缓存**：输入哈希 → 输出文件的哈希列表。
4. **调度器**：把待执行的动作派给 worker。
5. **worker**：取输入、执行命令、上传输出。

我们的设计与这五个部件一一对应（第 6 节）。差别在调度：通用系统不看关键路径，我们看。

### 2.3 Lean 与通用编译的五点不同

1. **输入大**。C 文件的输入是几十个头文件；Lean 模块的输入是整个导入闭包的产物，Mathlib 下游的模块动辄几千个文件、几个 GB，靠内存映射读入。
2. **每个模块有很重的固定开销**。`import Mathlib` 在我们的机器上单核约 6.1 秒（实测）。文件多而小的仓库，大部分工作量是重复导入。
3. **依赖链深**。黎曼猜想归档的导入图有 203 层（实测），最长链决定下限。
4. **产物里有路径**。带 linter 消息的模块会把源文件的绝对路径写进产物（公开 [D1][D8]，本机复现），所以各机器要用同一个路径才能逐字节一致。
5. **构建工具的调度在大机器上用不满核**。原版 Lake 在 192 线程时卡在内部的锁上，只能降到 64 线程（公开 [D1]；另一次独立复现在 288 核上也看到 Lake 线程大部分时间在等锁 [D11]）；它给每个 `lean` 进程开满线程，比 1 线程多用 25% 的 CPU（实测，Mathlib 文件）。

## 3 Lean 构建的技术事实

### 3.1 Lake 怎么构建（源码，Lake 4.33 [S6]）

- **读依赖**：在 Lake 进程内解析每个文件头的 `import`（`Lean.parseImports'`），不编译。
- **调度**：每个模块是一个任务，等它 import 的各模块的任务完成后开始；任务在一个线程池里，大小是 `LEAN_NUM_THREADS`，默认本机核数 [S7]。任务都是默认优先级，没有按耗时或关键路径排序的逻辑；Lake 没有 `-j` 参数 [S6][D7]。
- **编译**：另起一个 `lean` 子进程：

  ```text
  LEAN_PATH=<各库目录> lean <lakefile 里的额外参数> <源文件绝对路径>
      -o X.olean -i X.ilean -c X.c --setup X.setup.json --json
  ```

  `setup.json` 里有模块名、包名、是否 module 系统、选项，以及**导入闭包里每个模块的产物路径**。
- **判断要不要重建**：每个模块有一个 `.trace` 文件，记输入哈希（源文件内容、各 import 的哈希、选项、额外参数、模块名、包名、Lean 版本）。输入哈希不含路径（实测：把别处建好的产物连同 trace 拷进新目录，Lake 认为是最新的）。
- **找 `lean`**：通过环境变量 `LEAN_SYSROOT` 或 `LEAN`。

### 3.2 所以能做什么

- 编译一步是“输入输出都是文件的独立进程”，可以放到任何一台有相同输入的机器上（MIT 的 8 机构建、我们的工具都是这么做的）。
- 照同样的参数直接调 `lean`，产物与 Lake 逐字节一致（实测：316、2,613、3,156 个模块的工程）。

### 3.3 产物与确定性

- 逐字节一致的条件：同一工具链、同一依赖产物、同一选项、**同一源码绝对路径**。
- 线程数不影响产物（实测：30 个 Mathlib 重文件，1、2、4、8 线程产物相同）。Lean 4.33.1 有过一个由并行引起的不确定模块，4.36 修复（公开 [D1][D5]）。
- 导出给内核检查的内容不含路径，所以导出文件的哈希与构建路径无关（公开 [D8]）。

### 3.4 资源

| 项 | 数字 | 来源 |
|---|---|---|
| `import Mathlib` 的固定开销 | 单核约 6.1 秒 | 实测 |
| 一个只 `import Mathlib` 的进程 | 私有内存约 0.5 GB，映射文件约 7.5 GB，同机的进程共享这些页 | 实测（本机） |
| 黎曼猜想归档顶端的模块 | 要映射近 100 GB 的产物；系统参数 `vm.max_map_count` 要调到 1,048,576 | 公开 [D8][D3] |
| 每个模块的 `setup.json` | 在黎曼猜想归档里平均约 6 MB，合计约 1 TB，建完即可删 | 公开 [D9][D1] |
| 全部产物 | 黎曼猜想归档约 99 GB（出处未核实），压缩成 Lake 缓存包约 4.9 GB [D8]；CFSG 约 208 GB [D14] | 公开 |
| 单个文件的多线程 | 2 线程快 1.44 倍，8 线程 1.47 倍 | 实测 |

### 3.5 Lake 的缓存接口（本机 `lake cache help`；[S1][S3][S5]）

`lake build -o <映射文件>` 记录“输入哈希 → 输出”；`lake cache put` 上传到 S3 兼容的存储；`lake cache get` 下载；`lake cache add --service` 让构建时按需取。哈希是 64 位的，不抗碰撞（Lake 的帮助文本与引入它的 PR 都这么说 [S3]）。社区对黎曼猜想归档的实测（公开 [D8]）：17.5 万个缓存包 4.94 GB，下载 4 分 47 秒，恢复 91 秒，原版 Lake 校验 44 秒。

### 3.6 内核复核

逐模块重放（`leanchecker`）每个模块独立、可分发；对完整导出，多线程的独立内核几分钟到半小时，官方内核单线程要数天（公开 [D1][D15]）。我们实测逐模块重放比构建还慢，所以它也要分发。

## 4 理论

模型是调度理论里的 **P | prec | C_max**：相同处理机、任务有先后约束、最小化完工时间（文献与核对见 `docs/scheduling-theory.md`）。

- 下界：T ≥ max(W/C, CP)。
- 任何“有空核就派”的贪心：T ≤ W/C + (1 − 1/C)·CP（Graham 1966 [T1]）。
- 令 x = C·CP / W：T ÷ 下界 ≤ 1 + min(x, 1/x)。

| x | 情形 | 该做什么 |
|---|---|---|
| ≪ 1 | 核数少于可并行度 | 加机器，近乎线性；调度规则无所谓 |
| ≈ 1 | 拐点 | 调度规则最多差一倍，用“剩余最长链优先” |
| ≫ 1 | 核数多于可并行度 | 加机器没用；缩短最长链（多线程、拆文件、删 import）或靠缓存 |

已知结果：求最优是 NP 难的 [T9]；近似比好于 4/3 是 NP 难的 [T10]；“剩余最长链优先”在单位时长的入树上最优 [T3]，实践中接近最优 [T7]。带通信延迟时有“粒度”的概念：任务时长 ÷ 通信时间越大，预先切分越不重要 [T16]。我们的粒度在 1 万量级。文献与核对记录见 `docs/scheduling-theory.md`。

## 5 已有的证据

### 5.1 调度

| 结论 | 数字 | 来源 |
|---|---|---|
| 剩余最长链优先离最优 | 平均 0.5%–1.1%，最坏 3.9%（101 个子图，89 个证明了最优） | 精确 |
| 整个 Mathlib 上离更紧的下界 | 不到 0.5% | 模拟 |
| Lake 式“先就绪先派” | 拐点处慢 18%–24%，最坏 44% | 模拟、精确 |
| 预先切块 | 对看数据所在、产物建完即推送的动态派发：通信慢到模块耗时的 10 倍也没赢过（模拟）。工具现在不看数据所在、开工时才取件：每次取件多等 10 秒时按目录切块 580 秒对动态派发 894 秒，切块快 35%；多等 1 秒时动态仍快 8%（实测，两机） | 模拟；实测 |
| 静态计划 | 耗时估计有 30% 的误差就慢 24%–35% | 模拟 |
| 分批 | 每任务额外开销低于 0.2 秒时不该分批；我们是 4 毫秒 | 模拟、实测 |

## 6 目标架构

### 6.1 部件

```text
客户端/协调器 ──► 依赖图分析 ──► 缓存键 ──► 查动作缓存 ──► 未命中的模块进入调度
        │                                                        │
        │                                              就绪队列（剩余最长链优先）
        │                                                        │
        ▼                                                        ▼
   产物库（内容寻址）◄──── worker：取输入 → lean → 传输出 ◄──── 派发
        │
        ▼
   组装 → 校验（Lake 认可、逐字节比对、内核复核）→ 打包缓存 → 发布
```

| 部件 | 职责 | 关键设计 |
|---|---|---|
| 分析 | 读 `lakefile` 与 import 头，得到模块、依赖、每个库的选项；估计每个模块的耗时与内存 | 只读，不执行仓库代码；耗时用历史记录，没有就按行数 |
| 缓存键 | 每个模块：哈希（源文件内容，各直接依赖的键，工具链版本，选项与额外参数，包名与模块名，源码路径） | 用 SHA-256；键沿依赖传递，上游变了下游自动失效 |
| 动作缓存 | 键 → 产物文件的哈希列表 | 续建、增量、去重都靠它 |
| 产物库 | 文件按内容哈希存放 | 接口固定，后端可换：目录、HTTP、对象存储 |
| 调度器 | 维护模块状态；就绪模块按剩余最长链排序；派给空闲 worker | 快机器优先拿关键模块；核紧张时每个 `lean` 1 线程，核富余时 2 线程；大内存模块只派给大内存机器 |
| worker | 常驻进程，主动领任务；取导入闭包里本机没有的产物；照 Lake 的方式调 `lean`；上传产物 | 只向外连接；本地盘缓存产物；心跳 |
| 校验 | 组装全部产物；原版 Lake 认可；与参照逐字节比对；内核复核 | 复核任务与构建任务用同一套派发 |
| 打包与恢复 | 清单加产物；导出成 Lake 原生缓存格式 | 使原版 Lake 用户无需我们的工具 |
| 记录 | 每次尝试一行：就绪、派发、开始、结束、所在机器、CPU、内存、取产物耗时 | 供调参、校准模型、下次估计耗时 |

### 6.2 稳健性

1. 一切以产物库和动作缓存为准，协调器无持久状态；任何时候杀掉重跑都从缓存接着建。
2. 产物先写临时名再改名；下载必核哈希。
3. 一个模块失败就换一台机器重试；两台都失败判为源码问题，只跳过它的下游。
4. worker 上报工具链与依赖的指纹，不符就不派活。
5. 超时与心跳丢失按失败处理。

### 6.3 两种落地方式

| 方式 | 做法 | 适合 |
|---|---|---|
| 自带协调器与 worker（现在的工具） | 一个协调器进程，各机器上起 worker，经 SSH、作业调度系统或容器编排启动 | 没有现成构建集群；需要按关键路径调度 |
| 架在通用的远程执行集群上 | 部署一套开源的远程执行服务，客户端把每个模块包装成一个动作，用动作的优先级字段表达关键路径 | 已有这类集群，或想复用它的存储、缓存、监控 |

第二种没有试过。已知的开销都随每个动作的输入文件数增长，而 Lean 的一个动作要声明整个导入闭包（几千到十几万个文件）：客户端要为每个动作算输入树的 Merkle 树并查询缺失的对象（Bazel 有数十万个输入的动作单步要几秒、主进程内存不足的公开报告 [S11]）；worker 若在本地目录里逐个硬链接输入，Buildbarn 的文档明说大输入根初始化慢，改用 FUSE/NFSv4 虚拟目录可以按需加载 [S17]，但 Lean 基本会读取全部导入的 `.olean`，按需加载能省多少、内存映射在虚拟文件系统上表现如何，没有找到资料。各服务端对优先级字段的方向和默认开关也不一致 [S17]–[S20]。没有找到文档给出输入规模的上限，需要实测。

代码在 `lakeshard/`（公开仓库里是工具的快照）。

## 7 假设有一个集群：怎么做

### 7.1 对集群的要求

| 项 | 要求 | 原因 |
|---|---|---|
| 系统 | Linux x86-64，各节点同一发行版更省事 | 工具链是预编译的 |
| 核数 | 总核数取可并行度的 1–2 倍：Mathlib 约 40–80 核，黎曼猜想归档约 500–1,000 核 | 再多没有收益 |
| 内存 | 每核 4 GB；另要一台大内存节点（黎曼猜想归档 256 GB）跑顶端模块和导出 | 导入闭包的内存映射 |
| 本地盘 | 每节点能放下全部产物（黎曼猜想归档约 100 GB，另加依赖约 10 GB），SSD | 每台最终要持有九成以上的产物 |
| 网络 | 节点间 1 Gbit/s 以上，延迟毫秒级；worker 能连到协调器与产物库 | 粒度足够粗，1 Gbit/s 已够 |
| 路径 | 各节点用同一个绝对路径放源码 | 产物逐字节一致 |
| 系统参数 | `vm.max_map_count` ≥ 1,048,576；进程数限制够用 | 大闭包的映射数 |
| 隔离 | 第三方仓库在容器或沙箱里建，无外网、无凭据 | 编译会执行仓库代码 |
| 工具链分发 | 各节点能拿到同一份工具链与依赖产物（共享盘、镜像或从产物库取） | 指纹一致 |

### 7.2 定规模

1. 分析仓库得到 W、CP（没有历史耗时就先按行数估，再用一次小规模试跑校准）。
2. 核数 C 取在 x = C·CP/W 约 1 到 2 之间。
3. 查导入闭包大小的分布，决定大内存节点的数量。
4. 用模拟器预测用时，作为验收的参照。

### 7.3 流程

1. **准备**：每个节点装工具链、取依赖的官方缓存、放源码快照；起 worker；每个 worker 自测速度并上报指纹。
2. **试跑**：取导入图底部的一小块（几百个模块），多机构建，与单机 Lake 逐字节比对。不一致就停。
3. **全量**：协调器开跑；监控就绪队列长度、各节点利用率、失败数、与预测的偏差。
4. **校验**：组装；原版 Lake 认可；内核复核（逐模块重放分发到各节点；需要时导出后跑独立内核）。
5. **发布**：打包缓存，标记为已复核。
6. **留档**：运行记录、逐模块耗时（下次用）、与预测的对比。

### 7.4 不同的集群形态

| 形态 | worker 怎么起 | 注意 |
|---|---|---|
| 几台能 SSH 的机器 | SSH 起常驻 worker | 现在的做法 |
| 作业调度系统（如 Slurm） | 提交一个作业数组，每个作业是一个 worker，向协调器领任务 | worker 分批到位，协调器要容忍 worker 中途加入和离开 |
| 容器编排（如 Kubernetes） | 一个 worker 的部署加自动伸缩，协调器与产物库是服务 | 进程数、内存映射数、临时盘大小的限制要先查 |
| 云上按需机器 | 开跑时租，跑完释放 | 黎曼猜想归档 512 核约 70 分钟，按核·时计费约 600 核·时（预测） |

### 7.5 预期

| 仓库 | 集群 | 预期用时 | 相对单机 |
|---|---|---|---|
| Mathlib | 64 核 | 约 20 分钟（每文件 2 线程约 14 分钟） | 单机 16 核原版 Lake 47.7 分钟 |
| 黎曼猜想归档 | 512 核 | 约 70 分钟 | 单机 48 核 7–10 小时 |
| 黎曼猜想归档 | 128 核 | 约 3.9 小时；合并小文件后约 2.2 小时 | 同上 |
| CFSG | 未定 | 没有模型；先做分析得到 W、CP | 单机 6–22.5 小时 |

## 8 分阶段路线与验收

每一阶段都有可以独立验收的结果。

| 阶段 | 要跑通什么 | 验收标准 | 现状 |
|---|---|---|---|
| **第一步：单机上的黑箱** | 一个小的真实仓库（几百个模块，依赖 Mathlib），一条命令：仓库进、缓存出、恢复 | 产物与原版 Lake 逐字节一致；缓存放进全新检出后原版 Lake 不重编；中途杀掉重跑能接着建；改一个文件只重建受影响的模块 | 构建与比对已通；缓存被 Lake 认可、续建与增量未完成 |
| **第二步：多机有收益** | 合成仓库与 Mathlib 在三台机器上 | 用时相对单机原版 Lake 的倍数与理论预测相符（误差 15% 以内）；产物逐字节一致；几种对照（切块、不排优先级、Lake 加转发）都更慢 | 合成仓库一条实测 1.84 倍；Mathlib 未测 |
| **第三步：稳健** | 故障注入：杀 worker、断网、损坏产物、指纹不符、源码错误 | 每种情况都能自动恢复或给出明确报告，不产生错误的缓存 | 重试与下游跳过已有；其余未测 |
| **第四步：集群上的大仓库** | 黎曼猜想归档在一个约 500 核的集群上 | 用时在预测的 ±30% 内；产物与公开的清单或导出哈希一致；内核复核通过 | 待集群 |
| **第五步：持续使用** | 仓库更新后的增量构建；多个仓库共用缓存 | 增量构建的用时与改动量成正比；缓存命中率有统计 | 未做 |
| **第六步：服务化** | 提交 Git 链接，返回缓存地址 | 排队、多用户、隔离、配额 | 未做 |

第一步是最该先完成的：它不需要集群，却验证了整个黑箱的头和尾。

## 10 风险与未知

| 风险 | 影响 | 应对 |
|---|---|---|
| 补不出让 Lake 认可的 trace | 缓存只能被我们的工具使用 | 最后一遍用原版 Lake 在已有产物上封口；或借鉴社区为黎曼猜想归档做的 trace 重建 |
| 还原 `lean` 参数不完整（自定义选项、插件、动态库） | 产物与 Lake 不一致 | 每个新仓库先抽样比对；不支持的特性明确报错 |
| Lean 版本升级改变调用方式或产物格式 | 工具要跟着改 | 把调用方式集中在一个模块；对每个支持的版本跑一致性测试 |
| 顶端模块的内存需求超过任何一台机器 | 建不完 | 预先按闭包大小估算并提示；合并顺序或换大内存节点 |
| 共用机器的负载波动 | 计时不可信 | 每格三次取中位数；记录负载；关键实验用独占机器 |
| 耗时模型在黎曼猜想归档上不准 | 预测偏差 | 先建一个子闭包校准固定开销，再做全量 |
| 第三方仓库的恶意元程序 | 泄露或破坏 | 隔离执行；worker 不放凭据；缓存先标未复核 |
