# 大型 Lean 仓库多机构建：一页结论

> 本文原是研究线的工作报告。文中 `sim/…`、`results/…`、`data/…`、`scripts/…`、`t1_optimality.py` 等路径都相对于本仓库的 `study/` 目录；实验运行记录在 `bench/results/`。

2026-11-25。标记：**实测**（机器上量的）、**精确**（求解器证明的最优）、**模拟**（实测 trace 驱动）、**预测**（模型外推，待验证）。依据与细节见 `docs/study-report.md`。

1. **最优算法：剩余最长链优先的动态派发**——有空槽就把“到终点最长的就绪模块”派出去，耗时用上一次的记录或按行数粗估。离最优：子图上平均 0.5%–1.1%、最坏 3.9%（**精确**，89 个证明最优的实例）；合成工程 4 核最优 383.1 秒、它 383.3 秒（**精确**）；整个 Mathlib 在任何核数下离下界 < 0.5%（**模拟**）。Lake 那样按就绪先后派，在拐点处慢 18%–24%、最坏 44%。更复杂的算法（求解器、学习型、前瞻）能赢的不到百分之一。只看图结构不看耗时会慢 6%–37%。
2. **什么时候加机器有用**：先算仓库的可并行度 W/CP（总工作量 ÷ 最长链）。核数 C 小于 W/CP 时加核近乎线性；C ≈ W/CP 是拐点，调度规则在这里最值钱；**C 超过 W/CP 的 2–3 倍后加机器没用**，时长停在最长链（**模拟**，Graham 界给出同样的形状）。
3. **加机器没用以后**：只剩缩短最长链——每个文件给 2 个线程（Mathlib 20 → 14 分钟，**模拟**），删关键链上不必要的 import（Mathlib 一条最多省 93 秒），拆重文件（单个最多省 40 秒；Mathlib 的最长链是一条带，松弛 ≤ 2% 的模块有 496 个），或者靠缓存不建。去掉传递冗余的 import 对上限没有任何帮助（可证明）。
4. **该不该切**：**不要预先切块**（按目录、沿导入链、静态计划都不要）。内网传输（0.2 毫秒、1 GB/s）下放置完全无所谓；传输慢到模块耗时的 1/3 以下时要“数据在哪就派到哪”，但仍是动态派；一直到传输比模块慢 10 倍，预先切块都没赢过（**模拟**）。静态计划遇到 σ = 0.3 的耗时误差就慢 24%–35%，只用来预估。每模块一个任务，开销 ≤ 0.2 秒时不分批。
5. **线程怎么给**：核紧张时每个 `lean` 1 线程（Mathlib 文件开 16 线程多用 25% CPU，**实测**）；有空核时空核分享、每文件最多 2 线程（2 线程 1.44 倍、8 线程 1.47 倍，**实测**）。
6. **机器快慢不同**：同一模块在三台机器上 1.0 / 1.44 / 1.12 倍（**实测**）；关键模块应派给快机器（“最早完成”放置省 2%–10%，**模拟**）。每次大构建前在每台 worker 上测一次速度。
7. **预测准不准**：给定每台机器的速度、worker 开工时刻和每任务开销，模拟器对三机实测 419.4 秒的预测误差 −1% 到 +4%（**实测 vs 模拟**），单机原版 Lake −2%；不管机器差异的“运行前预测”低估 21%（慢机器 50 秒、开销 23 秒、等 worker 13 秒）。一次受最长链限制的运行本身有约 ±15% 的起伏。
8. **黎曼猜想归档怎么建（预测）**：工作量由每个文件的固定导入开销 F（启动 + `import Mathlib`，单核**实测** 6.1 秒）决定：F = 2 / 4 / 6.1 / 8 秒时 W = 276 / 373 / 476 / 568 核·时，CP 0.79–1.01 小时；F = 6.1 秒时 128 核 3.9 小时、512 核 69 分钟、2,048 核 56 分钟，超过约 1,000 核基本不再变快。合并同目录、同导入深度的小文件能把 W 砍 40%–70%，但会把同层本可并行的文件串起来、拉长最长链，所以按集群大小选：128 核时大胆合并（约 2.2 小时），512 核时只合并松弛 ≥ 50% 的文件（64 分钟），2,048 核时合并无益，只有让导入变快才行（F = 2 秒时 47 分钟）。先在目标机器上实测 F。
